## Research Question

The owner decided, 2026-10-26: adoption of an unvouched actor **rotates** the
passphrase (not refuse); the three inbound items ship together in **3.16.0**;
and report 2 (a list item cannot exceed one storage row) should be addressed
as far as a minor allows. Two questions remain:

1. How do app-created actors get vouched, and what exactly does the adoption
   rule do?
2. What does report 2 mean for the consumer, what can a minor deliver, what
   does it cost, and what stays next-major?

## Part 1: vouching and adoption

### The marker

`store.auth_method` (the actor's internal attribute store) already exists
and is written by exactly one creation path (web and SPA OAuth create,
`oauth2.py:1019`, value `"<provider>_oauth2"`). It becomes the marker every
creation path writes:

| Creation path | Value | Vouched? |
| --- | --- | --- |
| Web and SPA OAuth create (`oauth2.py:1009`) | `"<provider>_oauth2"` (unchanged) | yes |
| MCP OAuth server create (`oauth2_server/oauth2_server.py:837`) | `"<provider>_oauth2"` (new; today writes nothing) | yes |
| JSON factory and HTML form fallback (`handlers/factory.py`) | `"factory"` (new) | **no** |
| `trustee_root` instantiation (also through the factory) | `"factory"` | **no** |
| App code via `ActorInterface.create()` | new keyword-only `auth_method: str = "app"` | yes |
| OAuth2 system actor (`oauth2_server/system_actor.py:38`) | `"system"` | n/a, never logs in |
| Pre-3.16 actors | absent | **no** |

Mechanics: the keyword is added to `ActorInterface.create()` and to
`Actor.create()` beneath it (additive, defaulted, so a patch-compatible
signature change). The two library OAuth paths pass the provider value
through the keyword instead of writing `store.auth_method` after the fact,
so the marker lands in the same create call that fires `actor_created` and
a consumer's hook can read it. The factory handler calls `Actor.create()`
directly and passes `"factory"`. The default `"app"` means a consumer that
creates actors for its users' addresses and keeps the passphrase for API use
is vouched without a code change; a consumer that wants its own actors
treated as unvouched passes `auth_method="factory"` or any other value and
the adoption rule below treats only the vouched set as vouched.

Vouched set: any value other than `None` and `"factory"`. A fixed deny-list
rather than an allow-list, so a consumer's own values (`"import"`,
`"migration"`) are vouched by default, which matches the owner's compatible
choice.

### The adoption rule

Today two implementations look up an actor by creator and adopt it:
`oauth2.py:948-1003` (`lookup_or_create_actor_by_identifier`, reached by
every web, SPA, factory-cookie and email-form path) and
`oauth2_server/oauth2_server.py:826-832` (the MCP OAuth server's own copy).
The MCP copy should be replaced by a call into the first, or both should
call one new module-level function; the rule must never exist twice.

When the lookup finds an existing actor whose `auth_method` is `None` or
`"factory"`:

1. Generate a new passphrase (`config.new_token()`), write it with
   `DbActor.modify(passphrase=...)`, which exists on both backends
   (`db/dynamodb/actor.py:110`, `db/postgresql/actor.py:167`,
   `db/protocols.py:68`) but is not reachable from `Actor.modify()`, which
   takes only `creator` (`actor.py:439`). Add `passphrase` there, updating
   the in-memory value too.
2. **Only if that write returned true**, write `store.auth_method =
   "<provider>_oauth2"` and `store.auth_method_adopted_from = <old value or
   "legacy">`. Marker first and rotate second would, on a failed second
   write, leave a vouched actor with the squatter's passphrase live;
   rotate first and marker second only re-rotates on the next login.
3. Log one WARNING naming the actor id, the previous marker, and the peer
   ids of every trust relationship present at adoption. A trust row created
   with basic auth before adoption carries a secret that `check_token_auth`
   still resolves to a relationship; rotation does not touch it. The list in
   the log is what lets an operator, or the consumer's `oauth_success`
   hook, decide whether to remove them.
4. Continue as today: `oauth_provider`, `clear_pending_email_verification`,
   return the actor.

A vouched actor adopts as today, no rotation. The legitimate owner of a
rotated actor who still needs the passphrase reads it from `GET /<actor_id>`
with their session token (`auth.py:374-409` resolves it to the creator
relationship, `handlers/root.py:62-66` returns the passphrase).

**Behavior change** for the changelog and the migration guide: the first
OAuth login into an actor created through the JSON factory, the HTML form
without OAuth, `trustee_root`, or before 3.16 (no marker) invalidates that
actor's existing passphrase. Deployments that create actors through the
factory *and* let the same users log in with OAuth, and that hold the
passphrase somewhere, must read the new one after the first login or create
their actors through `ActorInterface.create()` instead. The residual
(pre-adoption trust rows and subscriptions survive) is stated in both.

### The switch

`with_open_factory(enable: bool = True)` → `config.open_factory`, default
on. Gate in `RootFactoryHandler.post()`, not in the route: when off, both
the JSON request and the HTML form's no-OAuth fallback answer 403 (the form
only ever reaches the handler when OAuth is not configured, in which case
nothing else could create an actor there, so 403 is the honest answer).
`GET /` and `/login` are unchanged. `trustee_root` instantiation is closed
with it, which the documentation names as the deviation from
`docs/protocol/actingweb-spec.rst:560-566`. The library's own integration
tests and the consumer's e2e tests create actors through the factory and
keep working on the default; the consumer turns it off in production from
its own environment, not from a library tie to `devtest`.

### SPA `prompt`

- `OAuth2Authenticator.create_authorization_url(..., prompt: str = "")`.
- `OAuth2Provider.authorize_prompt_params(requested: str) -> dict[str, str]`
  beside `authorize_extra_params()` (`oauth2.py:122`): the base returns `{}`
  (drop), Google returns `{"prompt": f"{requested} consent"}` so refresh
  tokens keep arriving, Apple and GitHub inherit the base.
- `POST /oauth/spa/authorize` reads `prompt`; accepted values
  `select_account` and `login`; anything else answers 400 like the other
  validated fields in `handlers/oauth2_spa.py:416-445`.
- Tests in `tests/test_oauth2_spa.py`; one paragraph in
  `docs/guides/spa-authentication.rst`.

## Part 2: report 2, in plain terms

### What the consumer has

Emm stores each output document as **one item** in a property list: the
body (Markdown or, since 2026-10-20, read-only HTML) together with its
metadata, serialised to one JSON string. A list item is one DynamoDB row
(`list:{name}-#{rank}`), and DynamoDB caps a row at 400 KB including the
key and attribute names. Emm therefore refuses any write whose serialised
row would exceed 380,000 bytes and answers a structured `output_too_large`
(its plan's Decision D2: "cap in v1, span later"). Typical reports are
8 to 12 KB; a long report with embedded images as data URIs hits the wall.
Emm has no way to store it and does not want to invent a layout over the
library's.

### What happens today, including a consequence the report did not reach

- The oversized write fails inside the SDK and surfaces as
  `DbError("property write")`, indistinguishable from any other fault.
- **Subscription diffs have the same cap.** A list-item `PUT` registers
  `{"index": i, "value": <the whole item>}` as the diff blob
  (`handlers/properties.py:787-791`), stored in a `SubscriptionDiff` row
  (`db/dynamodb/subscription_diff.py:32`, a plain string attribute). So
  even if items could be larger, any actor with a subscriber on that list
  would fail at the diff write. Any design for large items has to decide
  what a diff carries.
- PostgreSQL stores `TEXT` and has neither limit, so only DynamoDB shows
  either.

### What a minor can deliver: spanned items

A list item whose encoded value exceeds a threshold is stored as a small
**head row** at the item's existing key plus **body rows** in a key region
no existing reader looks at. Nothing about existing rows changes; no
migration; the feature is additive.

**Keys.** Head: `list:{name}-#{rank}` (unchanged), value an envelope such as
`{"__aw_span": 1, "gen": "<id>", "parts": 3, "bytes": 1048576}`. Body:
`list:{name}-$span-{gen}-{part:04d}`. The `$` (0x24) region sits after the
v2 item range, whose inclusive upper bound is exactly `list:{name}-$`
(`property_list.py:481`), before the v1 digit range (0x30 onward) and the
`-meta` row, and under the `list:` prefix that plain-property reads exclude
on both backends (`db/dynamodb/property.py:772`,
`db/postgresql/property.py:845`). So body rows are invisible to every
existing item read, and every list-row enumeration that exists today
**misses them** until taught; that list is below.

**Gen-keyed, not rank-keyed.** Body rows carry a per-write generation id, not
the rank. `compact()` rebalances rank keys by rewriting head rows
(`_v2_compact`, `property_list.py:2999`); bodies stay put. A rank move is a
head rewrite only.

**Write.** Put the body rows for the new gen (unconditional; the gen is
fresh, nothing references it), then the head through the existing
compare-and-swap (`set_if_value_equals` on the handle's raw value,
`property_list.py:2556`), then best-effort delete the previous gen's body
rows. A reader that read the old head keeps reading the old gen's rows,
which are immutable; a reader of the new head reads the new gen. **No
reader mixes generations**, and the handle contract is intact: the raw
value of a spanned item is its envelope, every write is a new gen, so
"the raw value changed" still means "the item changed since you read it".
This is the consumer's constraint 1 without `TransactWriteItems`.

**Read.** `_decode_item` sees the envelope and issues one `get_prefix` for
`list:{name}-$span-{gen}-` (`db/dynamodb/property.py:530`), joins the
parts in order, verifies the count, decodes. One extra Query per spanned
item, and only for spanned items.

**Delete.** Compare-and-swap delete of the head, then delete the body rows.
A crash between the two leaves body rows with no head: inert (no reader
reaches them), found and removed by `verify()`/`compact()`, which learn the
region.

**Where the work is.** Every site that enumerates a list's rows by range
must learn the `$span` region or it leaks body rows: `clear()`
(`property_list.py:1911`), `delete()` (`:1957`),
`sweep_foreign_format_rows()` (`:1855`), `_v1_item_names_in_range` and
`_v2_item_names_in_range` (`:1806`, `:1839`), `verify()` (`:2841`),
`_v2_compact()` (`:2999`), `migrate_to_v2()` and the v1 downgrade (a v1
list never spans; downgrading a list with spanned items refuses), the bulk
readers that group a partition dump (`fetch_all_including_lists` consumers
and `list_prefix_with_rows`, which must resolve envelopes), the
`scripts/verify_property_lists.py` and `scripts/migrate_property_lists.py`
scripts, and the handlers that serve items whole
(`GET /properties/{name}` and `/{index}`, which resolve). Row-level copies
(`scripts/migrate_dynamodb_to_postgresql.py`, export) need nothing: head
and body rows are ordinary rows.

**Threshold and ceiling.** Default threshold: the size at which the row
would otherwise fail (about 390 KB of encoded value, leaving room for the
key), so by default **no row that works today changes shape**. Configurable
lower (`with_list_item_span_threshold(bytes)` or a config field): a lower
threshold moves more bodies out of range scans, which is the consumer's
cost lever from `thoughts/research/2026-08-29-bulk-list-reads-from-a-consumer.md`
("no range read can exclude part of a row" stops being true for spanned
items). A hard ceiling on the whole item (default 4 MB, about eleven parts)
bounds read cost and the Query page size; above it, a new typed
`ListItemTooLargeError` is raised **before** any write, on both backends,
so PostgreSQL callers see the same error at the same size and the consumer
can drop its own 380,000-byte rule.

**Both backends run the same path.** Spanning is unnecessary on PostgreSQL
but running one code path under both CI backends is how this repo catches
divergence; the DynamoDB-only piece is the integration test that stores an
item over 400 KB against DynamoDB Local. Whether DynamoDB Local enforces
the 400 KB cap is **unverified** here; if it does not, that test asserts the
row shape (head plus N body rows) rather than relying on a backend error.

### The consumer's constraints, one by one

| Constraint | Met? | How |
| --- | --- | --- |
| 1. Atomic or generation-stamped commit; CAS still means "changed since read" | yes | gen-stamped body rows, CAS on the head envelope |
| 2. Cheap partial reads | mostly | range reads now pull a ~150-byte head instead of a ~400 KB row; resolution costs one Query per spanned item; the handle exposes `spanned` and `bytes` so a caller can skip resolution. A caller wanting app-level metadata without the body still has to keep metadata outside the body, as today |
| 3. Delete and rank moves cascade, no orphans | yes, with a sweep | delete cascades; gen keys make rank moves free; a crash can leave inert body rows that `verify()`/`compact()` remove |
| 4. One item for diffs and `/properties` | handlers yes, **diffs no** | a spanned item's diff carries `{"index", "spanned": true, "bytes", "value": null}` and the subscriber fetches the item. The full value cannot go in a diff row on DynamoDB. Not a regression: such items cannot exist today |
| 5. A DynamoDB test path | yes | integration test against DynamoDB Local, with the caveat above |

### What stays next-major

The per-partition 1 MB Query page ceiling and the general out-of-band
payload design remain in `thoughts/todo/prop-list-key-prefix-scheme.md`.
Spanning does not raise the ceiling; it does remove the bodies of spanned
items from range scans, which is a partial answer to that todo's second
requirement and should be recorded there when the todo is amended.

### Alternatives considered

- **Decline; consumer sidecar.** Zero library cost; the consumer writes
  body chunks to a second list and loses atomicity and CAS across the two.
  What the triage proposed before the owner asked for more.
- **Explicit attachment API** (`append(item, body=...)`, `get_body(handle)`).
  Solves constraint 2 fully (bodies never resolve unless asked) at the cost
  of a new API surface and a consumer rewrite. Not chosen: transparent
  spanning needs no consumer change and the handle flags give most of the
  benefit. Can be layered on later over the same rows.
- **`TransactWriteItems`.** True atomic multi-row commit, 100-item/4 MB
  limit, no PostgreSQL equivalent in the current layer, and the `$span`
  rows would still need the enumeration work. Gen-stamping gets the
  reader-visible property without it.

### Risk

Property-list storage is the code that caused the production list
corruption and has two dead whole-list-rewrite designs
(`thoughts/todo/whole-list-rewrite-atomicity.md`). Spanning is designed to
stay out of that failure class: it never rewrites an existing row, never
changes a head key, reuses the proven conditional-write primitive, and its
only new failure mode is an orphan body row, which no reader reaches and a
sweep removes. The risk that remains is an enumeration site missed in the
list above, so the plan's verification phase greps for every `get_range`,
`get_prefix` and `batch_delete` caller in `property_list.py` and the
scripts, not only the ones named here.

## Proposed shape of 3.16.0

Two plans, one release:

1. **Auth plan** (small, security): markers on every creation path, the
   single adoption rule with rotation, `with_open_factory`, SPA `prompt`,
   docs and migration guide. Ships to `master` first.
2. **Storage plan** (large): typed too-large error and the two wording
   fixes (`docs/quickstart/configuration.rst:590`, `property_list.py:5`),
   then spanned items with the enumeration audit, diff reference, handler
   resolution, DynamoDB test path, benchmark run (list storage changed).

3.16.0 is cut when both have landed. If the storage plan slips, the auth
plan ships as 3.16.0 on its own and spanning becomes 3.17; the security fix
is never held by the storage work.

Changelog shape: SECURITY (adoption rotation, with the **Behavior change**
sentence and the residual), ADDED (`with_open_factory`, SPA `prompt`,
spanned items, `ListItemTooLargeError`, `auth_method` on create), CHANGED
(spanned-item diffs carry a reference; the factory form fallback answers
403 when the factory is closed). `docs/migration/v3.16.rst` carries the
rotation note and the factory deviation.
