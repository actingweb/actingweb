# rc2 triage: what to act on from the v3.13.0rc1 consumer feedback

**Date:** 2026-07-25
**Input:** `2026-07-25-v3.13.0rc1-consumer-feedback.md`
**Library state:** `pyproject.toml` / `__init__.py` both `3.13.0rc1`; CHANGELOG
"Unreleased" is empty; working tree clean apart from the feedback doc.

> **SUPERSEDED 2026-07-26 — the recommendation below was reversed.** It was
> correct for the scope as it stood at the time (docs + an offline CLI + a
> logging fix). The scope then grew a hot-path change to `register_diffs()`,
> and two real subscription bugs surfaced. See "Decision reversed: rc2" at the
> end. The reasoning is kept because the *criterion* still holds — an rc is
> warranted exactly when something needs re-validation on DynamoDB — and it is
> what triggered the reversal once the premise stopped being true.

## Headline recommendation: ship **3.13.0 final**, not an rc2

The consumer has already validated rc1 *and completed their production
migration on it* — three deploys, both defects confirmed fixed by measurement
(1,872 → 98 RCU per fetch; ~1,396/min → 0 `DescribeTable`). rc1's payload is
proven in production.

Everything that survives triage below is either **documentation** or **purely
additive/observability-only code**. None of it changes a code path the consumer
exercised, so none of it needs another TestPyPI cycle and another round of
consumer re-validation. Manufacturing an rc2 to carry doc fixes costs a
validation cycle and buys nothing.

An rc2 would only be warranted if we chose to land **I0** (the hot-path range-key
change) — and both the consumer and this triage say that belongs in 3.14.

## Ship now (code — additive only)

1. **Offline table verifier** (`python -m actingweb.db.verify_tables`) — D1's
   real ask. Enumerates the required models for the configured mode and reports
   which are missing. Runs out-of-band with an operator's own credentials, so it
   is unaffected by the slimmed runtime role. Purely additive; no runtime cost.

2. **I2 — the suspension silent no-op.** Confirmed, and *narrower than the
   feedback doc claims*:
   - `suspend_subscriptions` (`actor.py:2089`) and `resume_subscriptions`
     (`actor.py:2115`) **already log at ERROR**. The doc's "all three return a
     benign default" is overstated.
   - The genuine silent path is **`is_subscription_suspended`
     (`actor.py:2067`) → `logger.debug`**.
   - Verified `pynamodb.exceptions.TableDoesNotExist` is a distinct class from
     `DoesNotExist`, so a missing table already escapes
     `DbSubscriptionSuspension.is_suspended()`'s narrow catch — the whole defect
     is that one `debug`.
   - The **PostgreSQL** accessor already logs operational errors at ERROR
     (`postgresql/subscription_suspension.py:37`); DynamoDB is the asymmetric
     one.
   - No test asserts the benign-default behaviour, so nothing locks it in.

   Fix: raise the caller's log level and distinguish "not suspended" from
   "couldn't tell". ~5 lines.

3. **Expose `auto_create_enabled()` as public API** (D9's second ask) — the
   consumer re-implemented the env parsing in their own trace-storage class.
   A re-export, nothing more.

## Defer to 3.14

- **I0 — `DbPropertyList.fetch()` reads the whole partition.** The most
  valuable finding in the feedback doc, and real: a list-heavy actor paid 1,027
  RCU to return 5 properties because ~1,009 `list:*` rows share the partition
  and are discarded client-side. But it is a hot-path rewrite: DynamoDB `Query`
  cannot `OR` on the sort key, so excluding the `list:` band needs **two**
  range-constrained queries (`name < 'list:'`, `name > 'list:~'`) plus a
  PostgreSQL equivalent plus tests — on a release already validated in
  production. `fetch_all_including_lists()` correctly keeps today's behaviour.
  Also worth auditing the trust/peer-trustee paths for the same shape. D7's
  operation counter is its natural acceptance test.

- **I1 — verify-and-report at startup when auto-creation is off.** Contradicted
  by the consumer's own production result: their runtime role ended up with
  *neither* `CreateTable` nor `DescribeTable`, and the doc itself flags that I1
  "would sit on a role that legitimately has neither permission." A
  `DescribeTable` sweep is therefore wrong for exactly the audience it targets,
  and a data-plane probe adds 8–9 calls per cold start — reintroducing the cost
  3.13 removed. The **offline** verifier above captures the value at zero
  runtime cost. Revisit only if a real need appears.

  **Reinforced by the autoscaling review:** a startup verification sweep runs
  on *every cold start*, so under load-based container churn its cost scales
  with the scale-up rate — reintroducing exactly the per-container control-plane
  traffic 3.13 eliminated, on the very deployments that care most. An offline
  pre-deploy gate is the correct shape for this check, not a runtime one.

- **I3 — fallback asymmetry / `use_lookup_table` three-sources-of-truth wart.**
  Documented via D3 for now. The config-plumbing cleanup is a breaking-ish
  refactor; pair it with the fallback-tier removal already scheduled for the
  next major.

## Not actionable

The "What works well" list — `_ensure.py` never caching a negative,
`reset_ensure_cache()`, concurrent pre-warm, fail-fast on legacy-mode-without-index,
the v2 digest design, `PAY_PER_REQUEST` in `Meta`, the backfill tripwire message.
Recorded so a future refactor doesn't regress them.

## Outcome (2026-07-25)

Decision: **docs + small additive code, released as 3.13.0 final.** Landed:

**Code**

- `actingweb/db/verify_tables.py` — new. `required_models()` /
  `required_table_names()` / `verify_tables()` plus a
  `python -m actingweb.db.verify_tables` CLI (`--list`, `--legacy`, exit
  0/1/2). Read-only; nothing runs at request time. Verified end-to-end
  against DynamoDB Local in all three states (all missing → exit 1, one
  missing → names it, all present → exit 0).
- `actingweb/interface/app.py` — `_prewarm_dynamodb_tables()` now consumes
  `required_models()`, so the created set and the documented set have one
  source of truth. A test asserts this wiring so it cannot silently drift.
- `actingweb/actor.py` — `is_subscription_suspended()` logs operational
  failures at ERROR naming actor/target/consequence, instead of DEBUG.
  Confirmed `TableDoesNotExist` is a distinct class from `DoesNotExist`, so
  a missing table does reach this handler. The ERROR is **one-shot per
  process** (`_suspension_check_error_logged`, mirroring `_ensure._flag_logged`):
  `register_diffs()` calls this on every property write, so an unconditional
  ERROR would flood the log at write rate — the same shape as the
  per-construction `DescribeTable` this release removed. **Revised after
  reviewing against an autoscaling deployment:** originally one-shot per
  process, now a 300s window. The reference app (`../actingweb_mcp`) runs
  Lambda container images with a deliberate 5-minute warmup ping, so its
  primary serving container lives indefinitely — "once per process" there
  means *once, ever*, reporting a broken suspensions table one time and then
  silencing every later failure, including a different one. A repeating
  heartbeat is alertable, self-terminating once fixed, and still bounded at
  one line per window per container under burst scale-up. The test asserts
  all three: first ERROR, throttled to DEBUG inside the window, re-armed
  after it.
- `actingweb/actor.py` — `register_diffs()` reordered: fetch subscriptions
  first and return early when empty, *then* check suspension. The log flood
  above was the symptom of a real per-write cost — an uncached DynamoDB
  `GetItem` on every property write, guarding a subscription list that is
  cached on the actor. With no subscribers both paths reach the same no-op,
  so the read bought nothing. Semantically neutral (suspended and
  no-subscriptions were already the same outcome); the 49-case end-to-end
  suspension flow passes unchanged against real DynamoDB. Two tests pin the
  ordering in both directions.

  Trade-off, disclosed in the changelog: an actor that is both subscribed
  *and* currently suspended now pays the subscription fetch it previously
  short-circuited past. Memoised per actor instance, and negligible beside
  the callback fan-out suspension exists to prevent.

  **Left alone deliberately:** `get_subscriptions()` caches via
  `if not self.subs_list`, so an actor with *zero* subscriptions re-Queries
  on every call — the empty list is falsy and never sticks. That accidental
  refetch is probably load-bearing for subscriptions created mid-instance
  (only the delete paths reset `subs_list`), so fixing the cache without
  adding proper invalidation on create would make new subscriptions
  invisible. Worth doing in 3.14 alongside I0, not in a validated release.
- `actingweb/db/dynamodb/__init__.py` — `auto_create_enabled()`,
  `set_auto_create()`, `reset_ensure_cache()` exported as public API.
- Tests: `tests/test_verify_tables.py` (new, 22 cases),
  one regression case added to `tests/test_subscription_suspension.py`.

**Docs**

- `docs/reference/database-backends.rst` — new `Required DynamoDB tables`
  section (keys, conditionality, the verifier command), plus the two rows
  missing from the schema-mapping table.
- `docs/migration/v3.13.rst` — D2 (deploy-sequencing race), D3 (direct
  accessor bypass), D4 (rollback needs the GSI), D5 (login path may not use
  reverse lookup), D6 (rehearse on DynamoDB Local), D7 (operation-profile
  recipe + the `get_session()` trap), D8 (PostgreSQL suite proves nothing),
  D9 (audit your own `DescribeTable` use), and the `ItemCount` ~6h staleness
  warning.

**Version:** `3.13.0rc1` → `3.13.0` in `pyproject.toml` and
`actingweb/__init__.py`; CHANGELOG rc1 section renamed to `v3.13.0: July 25,
2026` with new items marked *(since rc1)*, empty `Unreleased` retained.

**Gates:** pyright 0 errors / 0 warnings; ruff check clean; Sphinx builds with
both new cross-references resolving; `make test-all-parallel` → **2480 passed,
26 skipped, 0 failed** (stable across repeated runs). New tests also run green
under `DATABASE_BACKEND=postgresql`, which the CI matrix uses.

Three defects caught in review of this work, all fixed:

- `TestCli` asserted CLI exit codes without pinning `DATABASE_BACKEND`. The
  CLI exits 2 for non-DynamoDB backends, so all four cases failed under the
  PostgreSQL CI matrix job — i.e. this would have failed CI on the release
  commit. Fixed with an autouse fixture.
- The test helper stripped the table prefix by reading `AWS_DB_PREFIX` at call
  time, but pynamodb bakes it into `Meta.table_name` at *import* time, and
  other test modules reassign the env var (per-xdist-worker prefixes) without
  restoring it. Passed standalone, failed in the full run. Now asserts on
  suffixes only.
- The migration doc told operators to run the verifier "with the same
  environment as the app" — but an app selecting legacy mode via
  `with_legacy_property_index(True)` never sets `USE_PROPERTY_LOOKUP_TABLE`,
  so the verifier would default to lookup mode and report
  `_property_lookup_v2` MISSING on a correctly-configured deployment. Both
  docs now say to pass `--legacy`/`--lookup-table` explicitly in that case.
  (This is I3's three-sources-of-truth wart resurfacing; the 3.14 cleanup
  should subsume it.)

## Decision reversed: rc2 (2026-07-26)

The "no rc2" call above rested on one premise: *nothing in the delta touches a
path the consumer exercised, so nothing needs re-validation.* That premise
stopped being true.

**What broke it**

1. **The `register_diffs()` reorder is a hot-path change** on every property
   write — which, in the reference app (`../actingweb_mcp`, user memory stored
   as property lists), is the hottest path there is. I added it *after* making
   the "docs + additive only" call and did not revisit the call. That alone
   justifies an rc.
2. **Two real subscription bugs surfaced** while reviewing the deployment
   shape, both in the same subsystem as the release theme.

Sticking with "final" at that point would have been defending an earlier
decision rather than re-deriving it. There was also an inconsistency: I argued
I1 should be deferred *because* it adds per-cold-start reads, while shipping a
smaller instance of the same class of fix — deferring the bigger ones is not a
principled line if the criterion is "per-request read cost."

**Added in rc2, beyond what is listed above**

- `Actor.create_subscription()` invalidates `subs_list`. Subscriptions created
  through the interface layer previously received no diffs for the instance's
  lifetime — unbounded where MCP caches an `Actor` across requests.
- **Target-level suspension now cascades to subtargets** (both backends).
  `suspend_subscriptions("properties")` previously suppressed *nothing*:
  `PropertyStore` registers each diff with the property name as subtarget, so
  the check looked for `"properties:<name>"` against a stored `"properties"`.
  This is the functional half of the symptom the consumer reported — restoring
  the missing table alone would not have fixed their bulk import.
  `suspend()` deliberately keeps an *exact* check so a subtarget suspension
  under an already-suspended target is still recorded.

**Scope held back deliberately**

- **I0** (range-constrained property fetch). Two bounded queries is the right
  shape, but `Query` cannot `OR` on the sort key, so it doubles round trips on
  a latency-sensitive path — and the parallel alternative (a thread pool per
  fetch) is worse than the problem. That is an unresolved trade-off needing
  measurement (what fraction of actors carry `list:` rows? p50 delta for a
  light actor?), not an implementation squeezed in beside two other changes.
  Also worth confirming first whether the consumer's 1,027-RCU case ran
  through `fetch()` or `fetch_all_including_lists()` — the latter legitimately
  reads the whole partition and this design does not help it.
- **The `subs_list` cache guard.** Investigating it produced the most
  important finding of the pass: the obvious fix is *unsafe*, not merely
  second in line. See `thoughts/todo/subs-list-cache-asymmetry.md`.

**Acceptance — measured, not assumed**

Per the release's own D7 argument that these changes are invisible to
functional tests, the operation profile was counted against DynamoDB Local via
`BaseClient._make_api_call`, with a live-counter assertion so the zeros are not
vacuous:

| Exercise | Profile |
| --- | --- |
| Property write, no subscribers | `{GetItem: 1, PutItem: 1, Query: 1}` — no suspension read, no `DescribeTable`, no `Scan` |
| Subscribe, then write (same instance) | New subscription receives the diff |
| Write under a suspended target | `{GetItem: 1, PutItem: 1, Query: 2}` vs `{GetItem: 3, PutItem: 3, Query: 3}` un-suspended — diff and seqnr bump genuinely skipped |

The last row is the cascade fix working. Before it, suspended and un-suspended
writes had *identical* profiles, because suspension did nothing.

Note the integration suite's 49 suspension cases do **not** assert suppression
— several accept any status code and "document behaviour". Their passing was
never evidence for this, and I over-weighted it earlier.

Also confirmed live: `Query: 1` per write for an actor with no subscribers is
the open cost bug (Bug 2 in the todo), still there by design.

**Gates:** pyright 0/0, ruff clean, `make test-all-parallel` → 2486 passed,
26 skipped, 0 failed. Version `3.13.0rc2`; CHANGELOG restructured to an rc
section carrying an explicit re-validation note. Not tagged or pushed.

**Consumer action required:** rc1 is in their production. rc2 changes
`register_diffs()` read ordering, subscription-cache invalidation, and
suspension semantics. Pinning them forward is a real request, not routine —
flagged in the CHANGELOG note rather than left to the version number to imply.
