# Consumer feedback on v3.13.0rc1 (from the actingweb_mcp upgrade)

**Date:** 2026-07-25
**Library commit reviewed:** `c57b2cb` (Pre-release v3.13.0rc1)
**Source:** planning the `actingweb_mcp` upgrade 3.12.0 → 3.13.0rc1 against live
production (`ai.actingweb.io`, `eu-central-1`, 47 actors, `AWS_DB_PREFIX=AI`).
Consumer plan: `../actingweb_mcp/thoughts/plans/2026-07-25-actingweb-3.13-upgrade.md`

The rc fixes everything the original defect report asked for, and the fixes are
well-shaped (see "What works well"). This is feedback from being the *first
consumer to plan a real production upgrade* — the gaps are almost all in the
seam between the library and an IaC-managed deployment, not in the fixes
themselves.

Ordered by how likely each is to bite an operator.

---

## Documentation (`docs/migration/v3.13.rst`)

### D1 — There is no published list of tables that must pre-exist when auto-creation is off (highest impact)

"Recommended: disable auto-creation in production" tells operators to set
`AWS_DB_AUTO_CREATE_TABLES=false` and drop `CreateTable`/`DescribeTable` from the
runtime role, but never states **which tables the library then requires to
already exist**. The only table named is `_property_lookup_v2`, and only in the
narrower context of name-based IAM policies.

The authoritative list already exists in code —
`actingweb/interface/app.py:1338-1367`:

```
_actors  _attributes  _peertrustees  _properties  _subscriptions
_subscriptiondiffs  _subscription_suspensions  _trusts
+ _property_lookup_v2   (lookup mode only)
```

**Why this matters concretely:** auditing our prod against that list found
`AI_subscription_suspensions` **missing** — it had never been created, because
pre-3.13 the suspension accessor had no auto-create guard. An operator who
follows the doc (flip the flag, slim IAM) inherits a silently degraded
suspension path — see I2 for why it is silent. We only caught it because we
enumerated the models by hand.

**Ask:** publish the list in the migration doc and in
`docs/reference/database-backends.rst`. Better still, ship a verification
entry point (`python -m actingweb.db.verify_tables`, or a `--check` flag) so
operators can assert the precondition instead of reading source. This is also
the natural place to surface the CloudFormation resource shapes.

### D2 — The pre-warm ↔ IaC creation race isn't warned about

Because `_prewarm_dynamodb_tables()` runs at *integration time*
(`app.py:1448`, `:1479`), an upgrading deployment that declares the new tables in
CloudFormation/Terraform **in the same deploy as the library bump** can race:
the new container's first cold start creates `_property_lookup_v2` before the IaC
resource is created, and the stack then fails with `ResourceInUseException` and
rolls back.

We restructured our rollout into three deploys specifically to avoid this
(create tables first, still on 3.12; bump the library second; disable
auto-create third).

**Ask:** one note — "create the new tables in a deploy *before* the upgrade, or
let auto-creation own them; do not do both in the same deploy."

### D3 — Consumer code calling `DbPropertyLookup().get()` directly bypasses the fallback tiers

The three-tier read path (v2 → v1 → legacy GSI) lives only in
`DbProperty.get_actor_id_from_property()`. Anything constructing the lookup
accessor directly gets the **v2-only** path with no fallback.

In our repo that is 7 operational scripts (`manage_actors.py`, `debug_actor.py`,
`verify_lookup_tables.py`, `seed_demo_actor.py`, `revenuecat_cleanup.py`,
`migration_embed_outputs.py`, `backfill_output_link_ids.py`) — all of which
resolve an actor by email. Between the upgrade deploy and the backfill they
return `None` while the application itself is perfectly healthy. An operator
reads that as "the migration broke actor lookup" and may roll back a good deploy.

**Ask:** document that the migration window degrades direct-accessor consumers,
and name `get_actor_id_from_property()` as the supported entry point. See I3 for
the code-side option.

### D4 — The rollback instruction is unconditional, but rollback isn't always available

> Rollback: setting ``USE_PROPERTY_LOOKUP_TABLE=false`` (or
> ``with_legacy_property_index(enable=True)``) restores the legacy path.

For a properties table created before `PropertyIndex` existed, legacy mode
queries an index that isn't there. Our prod table is exactly this case (verified
live: `GlobalSecondaryIndexes: null`), so we have **no rollback path** — worth
knowing *before* upgrading, not after. The doc's own GSI-cleanup section makes
the same point in the other direction ("deleting the GSI makes a later return to
legacy mode impossible") but the rollback line doesn't carry the caveat.

**Ask:** qualify it — rollback requires the legacy GSI to be present on the
properties table; check `describe-table` first.

### D5 — "typically your login path" may overstate the backfill's urgency (minor)

The doc frames reverse lookup as "find-actor-by-email/oauthId — typically your
login path". In our app the authenticated-user path actually resolves via
`get_from_creator()` → the `creator-index` GSI on the actor table, so reverse
lookup is *not* on the login path at all. That materially lowers the risk of
deferring the backfill, and it's the kind of thing an operator should be told to
check rather than assume in either direction.

**Ask:** note both cases — apps resolving by creator are unaffected; apps
resolving by indexed property are the ones that must backfill promptly.

### D6 — Nothing tells operators how to *rehearse* the migration before touching prod

The riskiest step in this release is the backfill, and it is documented only as a
production procedure. But the whole migration — new-table creation, the
three-tier fallback, `backfill_property_lookup.py`, the startup tripwire — can be
rehearsed end-to-end against **DynamoDB Local** (`amazon/dynamodb-local`, with
`AWS_DB_HOST=http://localhost:8000`), at zero cost and zero risk. We only
realised this was possible after planning the whole rollout around production.

**Ask:** add a short "rehearse it first" subsection to the migration doc — start
DynamoDB Local, point `AWS_DB_HOST` at it, seed a couple of actors, run the
backfill, confirm the deprecation warnings stop. It converts a scary one-shot
production step into something an operator has already done once.

### D7 — There is no recipe for *proving* the fixes actually landed

Both headline fixes are invisible to functional tests: a `Scan`→`Query`
conversion returns identical data, and removing `DescribeTable` calls changes no
behaviour. A consumer who upgrades has no cheap way to confirm they got the win
short of reading CloudWatch on production.

There is one that works on **any** backend, including DynamoDB Local: count the
DynamoDB operations issued while exercising a hot path.

**Important gotcha, found the hard way.** The obvious implementation —
registering a `before-call.dynamodb` handler on a botocore session — **silently
counts nothing** with pynamodb. `pynamodb.connection.base.Connection.session`
resolves via `botocore.session.get_session()` (base.py:410), which returns a
**new** `Session` object per call, so a handler registered on any session
instance you can reach never sees pynamodb's traffic. The failure mode is a
counter that stays empty, which makes `assert scans == 0` pass **vacuously** —
worse than no test. Patch `BaseClient._make_api_call` instead; every botocore
client funnels through it:

```python
import botocore.client, collections

counts = collections.Counter()
original = botocore.client.BaseClient._make_api_call

def _counting(self, operation_name, api_params):
    if self.meta.service_model.service_name == "dynamodb":
        counts[operation_name] += 1
    return original(self, operation_name, api_params)

monkeypatch.setattr(botocore.client.BaseClient, "_make_api_call", _counting)
```

**Verified against both versions** (DynamoDB Local, identical test file):

| Exercise | 3.12.0 | 3.13.0rc1 |
| --- | --- | --- |
| `DbPropertyList().fetch(actor_id)` | `{'DescribeTable': 1, 'Scan': 1}` | `Query` used, **`Scan: 0`** |
| `DbTrustList().fetch(actor_id)` | `{'DescribeTable': 1, 'Scan': 1}` | **`Scan: 0`** |
| 25 × `DbProperty()` construction | **`{'DescribeTable': 25}`** | **`{}` — 0 calls** |

That is a clean, reproducible demonstration of both headline fixes, obtained in
seconds at zero cost. `DescribeTable: 25 → 0` for 25 constructions is exactly the
1-per-construction defect and its removal.

**Ask:** publish this (with the `get_session()` caveat — it is a real trap) in the
migration doc or release notes, and consider shipping it as a library test
helper so consumers can assert the operation profile in their own CI.

### D8 — "Run your test suite" is not sufficient validation for this release

Consumers whose local development defaults to a different backend cannot exercise
any of these fixes locally. Ours defaults to PostgreSQL
(`DATABASE_BACKEND=postgresql`), so our full suite — 2,652 tests, all green
against rc1 — touched **none** of the changed DynamoDB code paths. That is an
easy trap: a green suite reads as "validated" when the release's entire payload
is untested.

**Ask:** state plainly in the migration doc that validating 3.13 requires running
against a DynamoDB backend (local or real), and point at D6's rehearsal path.

## Implementation

### I0 — Residual: `DbPropertyList.fetch()` reads the whole partition, including every `list:` row (measured in production)

**This is the most valuable thing in this document.** The `Scan`→`Query` fix works and
its scaling benefit is real, but the per-call cost is far higher than "≈1 RCU"
because `fetch()` constrains only the **hash** key. Property-list items live in
the same partition under range keys prefixed `list:`, so a query for an actor's
plain properties reads all of them and discards them client-side.

Measured against the real production `AI_properties` table (16.7 MB, 43 actors),
same actor, same code path, only the library version changed:

| Actor's partition | 3.12.0 (`Scan`) | 3.13.0rc1 (`Query`) | Improvement |
| --- | --- | --- | --- |
| 86 rows (typical) | 1,872.5 RCU / 15 calls | **98.0 RCU / 1 call** | **≈19×** |
| 1,014 rows (heavy list user) | 1,872.5 RCU / 15 calls | **1,027.0 RCU / 9 calls** | ≈1.8× |

Both fetches returned **5** plain properties. So the heavy actor paid 1,027 RCU
to retrieve 5 items, because its partition holds ~1,009 `list:*` rows that the
query read and threw away. Its range keys look like:

```
created_at, displayname, email,
list:audit_instruction_agents-0, list:audit_instruction_agents-meta,
list:audit_instruction_tasks-0, list:audit_instruction_tasks-1, ...
```

**What the fix did and did not achieve.** It removed the *cross-actor*
superlinearity, which was the important part — one actor's data no longer
inflates every other actor's reads, and cost is now bounded by the caller's own
partition instead of total table size. What remains is *within-actor*
amplification proportional to that actor's property-list volume, which for a
list-heavy application (ours stores user memory as property lists) is the
dominant term.

**Ask:** constrain the range key too. Since `name` is the range key and list rows
share the `list:` prefix, plain-property reads can exclude them in the key
condition rather than client-side — e.g. a `name < 'list:'` / `name > 'list:~'`
pair, or better, a deliberate key-prefix scheme (`prop#` / `list#`) so each
access pattern is a single bounded range query. Conversely
`fetch_all_including_lists()` legitimately wants the whole partition and should
keep today's behaviour. Worth checking the equivalent trust/peer-trustee paths
for the same shape.

This does not detract from shipping 3.13 — it is strictly better than 3.12 on
every actor we measured. It is the natural next optimisation, and it is
invisible without per-call capacity instrumentation, which is why D7's recipe
matters.

### D9 — "Disable auto-creation" also breaks *consumer* code that probes its own tables

Follow-on from D1, and it bit us for real after the flag was live. The migration
doc frames `AWS_DB_AUTO_CREATE_TABLES=false` plus dropping
`CreateTable`/`DescribeTable` as a library-scoped change. It isn't: the IAM half
is account-wide, so **any** consumer code doing its own table-existence check
breaks too.

In our app, a custom trace-storage class calls raw boto3
`table.load()` — a `DescribeTable` — entirely outside the library. With the
permission gone it raised `AccessDenied`, its caller caught broadly and only
logged a warning, and AI tracing silently switched off while re-issuing the
denied call on every service construction. Nothing in the library was wrong; the
docs simply gave no reason to go looking.

We fixed it by having that class honour the same `AWS_DB_AUTO_CREATE_TABLES`
flag and skip its probe when tables are externally managed — which kept
`DescribeTable` at zero rather than restoring the permission.

**Ask:** when recommending the flag, add one line — "audit your own code for
`DescribeTable`/`CreateTable` use (boto3 `table.load()`, `describe_table`,
pynamodb `exists()`); the IAM change affects it too." Exposing the library's
`auto_create_enabled()` as public API would also let consumers reuse the same
switch instead of re-implementing the env parsing, which is what we ended up
doing.

### I1 — Disabling auto-creation also disables every table-existence check

`_prewarm_dynamodb_tables()` returns early when auto-creation is off
(`app.py:1335-1336`), and `ensure_table()` deliberately skips `exists()` in that
mode (`_ensure.py`, to avoid an `AccessDenied` per construction for roles without
`DescribeTable`). Both choices are individually right, but together they mean
**the most production-like configuration is the one with no startup safety net at
all.**

`ensure_table`'s docstring says the no-op is safe because "the caller's
subsequent data-plane operation will fail loudly if the table genuinely does not
exist." That holds for most accessors but **not** for the suspension path (I2),
which is precisely the table we found missing.

**Ask:** when auto-creation is off, optionally verify existence once at
integration time and log an ERROR naming any missing tables — a single
concurrent sweep, or a cheap `GetItem`/`Query` probe for roles that lack
`DescribeTable`. Gate it behind a flag so a locked-down role can opt out. This
reuses the pre-warm structure that already exists and converts D1's
read-the-source precondition into an actionable startup message.

### I2 — Subscription-suspension failures are swallowed to indistinguishability

`SubscriptionSuspension.is_suspended()` catches only `DoesNotExist`
(`subscription_suspension.py:60`), which is correct in isolation. But all three
callers in `actor.py` catch bare `Exception` and return a benign default:

- `is_subscription_suspended` → `except Exception` at `actor.py:2067` → `False`
- `suspend_subscriptions` → `except Exception` at `actor.py:2089` → `False`
- `resume_subscriptions` → `except Exception` at `actor.py:2115` → `0`

So "table missing", "IAM denied", and "not suspended" are the **same observable**.
With auto-creation off and the table absent, `register_diffs` treats every target
as un-suspended, and a bulk import's `suspend()` silently no-ops — so per-item
callbacks fire for every imported item, which is exactly what suspension exists
to prevent. No error surfaces anywhere.

**Ask:** distinguish `DoesNotExist` from operational errors and log the latter at
WARNING/ERROR (or let them propagate). A silent no-op is the worst outcome for a
correctness feature.

### I3 — Fallback asymmetry between the factory path and direct construction

Same root cause as D3. Two options: give `DbPropertyLookup.get()` the same
tiering as `get_actor_id_from_property()`, or have direct construction log a
deprecation-style warning pointing at the supported entry point. Either removes a
sharp edge for consumer tooling during every future lookup migration.

Related, still open from the original review: the `use_lookup_table`
config-plumbing wart (three sources of truth; direct construction falls back to
the env var and can disagree with the app-level setting) appears unchanged.

## Validation results (consumer side)

Run against rc1 from the `actingweb_mcp` working tree, 2026-07-25 (pre-deployment gate; production results are in the rollout-status section at the end):

- **Library's own fix tests:** 27 passed (`test_scan_to_query.py`,
  `test_conditional_gsi_schema.py`, `test_property_lookup_v2.py`).
- **Consumer suite on PostgreSQL:** 2,652 passed, 2 skipped, 0 failed. Note this
  proves nothing about this release — see D8; none of the changed DynamoDB code
  paths execute on that backend.
- **Consumer suite on DynamoDB Local:** 2,651 passed, 4 failed — and all 4
  failures are a harness artifact of our own making (Stripe webhook tests POST to
  a preview server still configured for PostgreSQL while the test process read
  DynamoDB, so the writes landed in a different database). The same 4 pass on the
  PostgreSQL run. **No rc1 defect found.**
- **Operation profile:** confirmed fixed, see the table in D7.
- **Reverse lookup end-to-end:** email→actor resolution returns the correct
  actor via the v2 path (`POST /api/auth/demo` → 200), and the persona re-seed
  (memory, instructions, outputs, agent tasks) writes cleanly under rc1.
- **Model metadata:** `SubscriptionSuspension.Meta.billing_mode` reports
  `PAY_PER_REQUEST` — Defect 3 in place.

**Production results — the rollout is complete and both fixes are confirmed live:**

- **Read amplification (Defect 1):** see the measured table in I0. Typical actor
  1,872.5 → 98.0 RCU per property fetch; cross-actor superlinearity gone.
- **`DescribeTable` (Defect 2):** measured from CloudTrail, attributed to the
  Lambda role:

  | State | Lambda `DescribeTable` |
  | --- | --- |
  | 3.12 (original finding) | ≈**1,396/min** |
  | 3.13, auto-create still on | **≈3.5/min** (memoisation working; residual is the per-container pre-warm sweep) |
  | 3.13 + `AWS_DB_AUTO_CREATE_TABLES=false` | **0** |

  Control so the zero is not vacuous: the window contained 15 invocations
  **including a cold start**, which is exactly when the pre-warm sweep would have
  fired. This confirms the design intent stated in I1 — memoisation fixes the warm
  steady state, and only the flag reaches zero.

- **Migration:** backfill wrote 41 rows matching v1 exactly, 0 collisions; reverse
  lookup then resolved from v2 with **no deprecation warning**; the startup
  tripwire stopped firing (verified by timestamp, not assumption).
- **IAM:** `CreateTable` and `DescribeTable` dropped from the runtime role with
  **no `AccessDenied`** — so the I1 suggestion (verify-and-report when
  auto-creation is off) would sit on a role that legitimately has neither
  permission, which is worth designing for.

One operational note worth adding to the migration doc: `describe-table`'s
`ItemCount` refreshes only every ~6 hours, so immediately after a successful
backfill the v2 table still reports `ItemCount: 0`. We nearly mis-read that as a
no-op backfill. `scan --select COUNT` gives the true figure. A one-line warning in
the runbook would save the next operator the same double-take.

## What works well (kept deliberately, please don't regress these)

- **`_ensure.py` never caches a negative**, and re-raises anything that isn't
  `ResourceInUseException` — including `AccessDenied`. That is the right call:
  swallowing it would turn a misconfigured role into silent data loss.
- **`reset_ensure_cache()` shipped as a test hook**, closing exactly the
  memoisation/test-isolation gotcha flagged in the original review rather than
  leaving the invariant accidental.
- **Pre-warm is concurrent** (`ThreadPoolExecutor` over the model list) and
  degrades to the lazy path on failure — the right shape for serverless cold
  starts, which is where the serial sweep hurt most.
- **Fail-fast on legacy mode with a missing index** (`property.py:257-274`)
  converts what was an opaque runtime crash on our GSI-less table into an
  actionable error.
- **The v2 digest design** (SHA-256 of `(name, value)`, no stored plaintext)
  simultaneously removes the 2048-byte key limit, fixes the value-only
  cross-name match, and improves the data map. Storing digests rather than
  values is worth calling out as a security improvement in release notes, not
  just a schema change.
- **`billing_mode = PAY_PER_REQUEST` in model `Meta`** means no future deployment
  can inherit the 2 RCU / 1 WCU login-path wall we hit.
- **The backfill tripwire message is genuinely good.** Observed firing against a
  fresh DynamoDB Local database:

  > Property lookup table is empty but the properties table has data: reverse
  > lookups (e.g. find-actor-by-email) depend on a deprecated fallback or will
  > return None. Run scripts/backfill_property_lookup.py to populate
  > 'devtest_property_lookup_v2'. See docs/migration/v3.13.

  It names the symptom, the exact script, the exact resolved table name, and the
  doc. That is the standard the D1 "which tables must exist" message should aim
  for — and it is why I1 (verify-and-report when auto-creation is off) feels like
  a natural extension of something you already do well, not a new idea.

## Rollout status: complete in production (2026-07-25)

`actingweb_mcp` is fully migrated. Sequenced over three deploys so no step
depended on an un-migrated state:

1. The two missing tables declared in CloudFormation, **ahead of** the library
   bump (avoids the D2 race).
2. Pin moved to `3.13.0rc1`, released and deployed.
3. Backfill run and verified, then `AWS_DB_AUTO_CREATE_TABLES=false` plus
   `CreateTable`/`DescribeTable` dropped from the runtime IAM role.

Every finding in this document came out of doing that, and each is reproducible
from the numbers quoted rather than from recollection. Full protocol and the
measured before/after live in
`../actingweb_mcp/thoughts/research/2026-07-23-scaling-review-apigw-lambda-dynamodb.md`;
the staged plan is in `../actingweb_mcp/thoughts/plans/2026-07-25-actingweb-3.13-upgrade.md`.

**Net verdict: 3.13 does what it set out to do.** The scan→query conversion
removed the cross-actor superlinearity that was the real scaling wall, and the
memoisation plus the opt-out flag took control-plane traffic from ~1,396/min to
zero. The two things worth your attention next are **I0** (the residual
whole-partition read, now the dominant per-call cost for list-heavy consumers)
and **D1** (publishing the table list that `AWS_DB_AUTO_CREATE_TABLES=false`
depends on — the one place we could have taken production down by following the
docs).

Happy to answer questions or re-measure anything on request.
