===========================
Migrating to ActingWeb 3.16
===========================

.. warning::

   This guide shows the API **as it evolved across this migration**. Where
   a block demonstrates the *previous* pattern, it must not be copied into
   new code; see :doc:`../guides/index` for the current API.

Start here
==========

3.16 closes a squat on the actor factory, makes a database fault an error
instead of a guess, makes ``with_unique_creator()`` a guarantee the database
enforces, and adds ``prompt`` to the SPA sign-in. Most applications need to
check only the first three items and item 11.

.. warning::

   **An application that calls ``with_unique_creator()`` does not start on
   3.16 until you have run ``actingweb-unique-creators``** (the demo
   application and ``actingweb_mcp`` both do). Run `Step 0`_ against the
   production database before the deploy; the application otherwise raises
   ``UniqueCreatorNotReady`` from ``integrate_flask`` / ``integrate_fastapi``.

1. **An actor created before 3.16 with no marker is cleaned at its first
   sign-in after the upgrade.** That covers the factory, the email form,
   direct ``Actor.create`` calls and the MCP OAuth server; actors the provider
   sign-in buttons created already carry ``<provider>_oauth2`` and are left
   alone. Its passphrase is rotated and its trusts, subscriptions,
   sessions and registered OAuth2 clients are removed (MCP connectors must
   register and authorize again); its data is kept. Install 3.16 and run
   ``actingweb-mark-actors-vouched`` *before the application serves its first
   sign-in* to skip that for actors you know are legitimate. **An application
   whose users signed up through an MCP connector must run it:** the MCP OAuth
   server proved those addresses through the provider but never wrote a
   marker, so they are real accounts that would otherwise be cleaned.
2. **Actors created through ``POST /`` after the upgrade are replaced, not
   cleaned,** at the first sign-in that proves their address: new actor id,
   data gone. If your deployment creates actors through the factory and later
   signs the same users in with OAuth, create them with
   ``ActorInterface.create()`` instead, or close the factory. The same goes
   for the factory form with ``www_auth="oauth"``: the actor it creates is
   replaced at the OAuth callback that follows, so ``actor_created`` fires
   twice (and ``actor_deleted`` once) for one first login. A replacement also
   deletes the other ``factory`` actors with the same creator, and a sign-in to
   a vouched actor deletes the ``factory`` actors beside it (``actor_deleted``
   fires for each; at most 10 per sign-in, not counting the actor a
   replacement removes, the rest at later ones), and a lookup
   by creator among several that share it prefers a vouched actor, then any
   other unvouched one, and takes a ``factory`` actor last: an owner's actor
   from before 3.16 beside a squatter's is the one cleaned, with its data.
3. **An OAuth-only deployment should close the factory:**
   ``.with_open_factory(False)``.
4. Code calling ``Actor.create`` or ``ActorInterface.create`` directly needs
   nothing for new ids: the new ``auth_method`` keyword defaults to ``"app"``.
   With a caller-supplied ``actor_id`` that is already taken, ``create`` now
   returns ``False`` (``ActorInterface.create`` raises) instead of ``True``.
5. MCP sign-ins now write the same actor fields as the other paths.
6. A hook on ``actor_deleted`` or ``actor_deleted_complete`` may now see
   ``reason="replaced_at_adoption"``.
7. ``Actor.modify`` now takes a passphrase and returns the backend result;
   ``Actor.delete`` returns a bool.
8. SPA clients can ask for account selection with ``prompt``.
9. A custom database backend must accept ``strict`` on every ``get`` (except
   ``DbProperty.get``, which takes none and always raises), ``fetch`` and
   ``get_bucket``, raise ``DbError`` on a fault, and accept
   ``consistent`` and ``ids_only`` on ``DbActor.get_by_creator`` (see
   `Fault contract`_).
10. ``PUT /<id>/trust/trustee`` with a new ``creator`` unvouches the actor;
    with ``force_email_prop_as_creator`` on it refuses an address other than
    the stored email.
11. **A database fault now answers 503, not a guess.** Reads that decide
    something raise ``DbError`` on a throttle or timeout instead of reading
    as "not found", and both integrations answer it with ``503`` and
    ``Retry-After: 5``. Code that catches ``Exception`` around
    ``ActorInterface`` calls and treats it as "absent" should let
    ``DbError`` through (see `Fault contract`_).
12. **``with_unique_creator()`` is enforced** (see `Creator uniqueness`_):
    a second actor for a creator raises ``CreatorTaken`` (409; the factory
    keeps its 403), the factory no longer returns an existing actor for a
    matching passphrase, and the application refuses to start until the
    command has enabled enforcement.
13. The factory form redirects an address that has an actor to ``/login``,
    not to ``/<id>/www``, and creators beginning with ``#`` or containing
    ``#dup-``, and ``system`` and ``oauth2-system``, are refused with 400.
14. **Property-list items larger than one row now span** (see
    `Spanned list items`_): on DynamoDB a v2 list item over 390,000 encoded
    bytes is stored across several rows instead of failing, an item over
    4 MiB raises ``ListItemTooLargeError`` (413 over REST) before any write,
    and PostgreSQL is unchanged at its defaults. **Deploy 3.16 everywhere
    before any client stores a larger item**: a pre-3.16 reader sees a
    spanned item as an envelope dict. ``$`` is refused in new list names and
    in a caller-supplied actor id, and a list diff over the threshold is sent
    as a reference.


What changed and why
====================

The factory squat
-----------------

``POST /`` creates an actor for any address nobody has claimed, with a
passphrase of the caller's choosing, and needs no authentication. Before 3.16
the address owner's first OAuth login adopted that actor as theirs with the
squatter's credentials still live: the passphrase, any trust relationship made
with it (including an ``admin`` trust to the squatter's own actor with a secret
the squatter chose), any subscription, and any property the squatter prefilled.

From 3.16 every creation path records how the actor came to exist in
``auth_method`` (see :doc:`../guides/authentication`), and a sign-in that proves
an address over an actor nobody vouched for no longer inherits it. The protocol
mandates the factory, so it stays; the fix is that a self-asserted ``creator``
can no longer be inherited as a verified identity.

Two populations, two behaviours
-------------------------------

.. list-table::
   :header-rows: 1

   * - The unvouched actor
     - At the first address proof
     - Data
     - Actor id
   * - Created before 3.16 with no marker (any path but the provider
       sign-in buttons, the MCP OAuth server included),
       ``email_unverified``,
       ``creator_changed`` (its creator was set through
       ``PUT /<id>/trust/trustee``), or ``email_verified == "false"``
     - **Cleaned in place**: passphrase rotated; every trust, subscription,
       SPA session, MCP token and registered OAuth2 client removed; stored
       provider tokens and ``trustee_root`` cleared; marked
       vouched
     - kept
     - unchanged
   * - Created through ``POST /`` after the upgrade (``factory``)
     - **Replaced**: deleted through the tested wipe and recreated
     - gone
     - new

*Cleaned in place* is for actors that may belong to their legitimate creator:
a pre-3.16 deployment's factory-then-OAuth users, and the self-asserted email
form's users, who by design hold a two-week session and real data before they
verify. Properties a squatter prefilled are **reported, not removed**: the
``actor_adopted`` hook carries their names so the application can inspect them.

An *address proof* is a provider login or the emailed verification link. The
link also runs the in-place rule before marking the address verified, so a
squatter whose provider profile carries the victim's address cannot keep a
session through a phished "verify your email" click. A user who verifies by
link therefore gets a new passphrase and has their sessions revoked: the
application should send them to sign in again after the click.

A user whose provider supplies no verified address reaches the free-text email
form at every sign-in, and that form answers ``409`` for an address that
already has an actor (as before 3.16). Such a user can sign in again once the
provider supplies the address, for example after verifying it at GitHub. The
verification click only moves the sign-out earlier: the session used to last
until it expired. The same ``409`` meets such a user whenever someone else
created an actor for their address through the open factory first, which is
one more reason for an OAuth deployment to close it.

No request leaves the process during either: the peer URLs on an unvouched
actor were chosen by whoever created it, so the wipe skips the remote
``DELETE`` calls and keeps every local cleanup. If the wipe cannot be
confirmed the sign-in fails closed (an ERROR is logged and the actor stays
unvouched), and the next sign-in retries. The status the client sees is
``502`` on ``/oauth/callback`` and ``500`` on the SPA authorize and token
endpoints and on the verification link.

Marking actors you trust before the first sign-in
-------------------------------------------------

An actor that already holds legitimate relationships should not be cleaned at
its next login. The tool ships with the library and needs 3.16: install the
upgrade, then mark the actors before the application serves its first sign-in,
with the application's own environment:

.. code-block:: bash

   actingweb-mark-actors-vouched --dry-run
   actingweb-mark-actors-vouched --marker operator
   actingweb-mark-actors-vouched --creator alice@example.com

(``python -m actingweb.maintenance.mark_actors_vouched`` and, in a source
checkout, ``scripts/mark_actors_vouched.py`` run the same code.)

The tool writes ``auth_method`` on actors that have none and leaves every
actor that already carries a marker alone. It resumes with
``--start-after <actor id>`` and scans the whole actor table (maintenance, not
a serving path). ``--include-factory`` also re-marks ``factory`` actors, for a
deployment that kept the factory open after upgrading and wants to vouch for
what it created; run that while no sign-in is served, since a sign-in replacing
one of those actors (or a sibling of it) deletes it whichever is first. A value that does not vouch (``factory``,
``email_unverified``, ``creator_changed``) is refused as ``--marker``. Every
actor the **MCP OAuth server** created before 3.16 is unmarked too, and the
same tool covers them.

Reading the output. The last line reports:

``scanned``
   Actors considered (after ``--creator`` and ``--start-after``).
``marked``
   Marker written and read back (or, with ``--dry-run``, would be).
``skipped``
   Already carried a marker; not touched.
``pending``
   Marked, but their email verification is still pending
   (``email_verified == "false"``). They stay unvouched and are cleaned at
   the sign-in that proves the address.
``errors``
   The marker could not be read or the write did not read back. Re-run;
   actors already marked are skipped.

A ``progress:`` line every 100 actors, and the closing
``last actor handled: <id>`` line, give the value for ``--start-after`` if the
run is interrupted. Once an actor has errored they say to re-run without
``--start-after`` instead: the actors that errored sort before that id.
Exit codes: ``0`` every actor was handled, ``1`` at least one error, ``2`` the
actor list itself could not be read and nothing was scanned (not a report of
zero actors), or an argument was refused, such as a ``--marker`` that does
not vouch; the message says which.

A cleaned-in-place actor's passphrase changes, so anything that stored the
old one must read the new one from ``GET /<actor_id>`` with the session token
(``Accept: application/json``).

Direct ``Actor.create`` and ``ActorInterface.create`` callers
-------------------------------------------------------------

Both take ``auth_method`` (default ``"app"``: the application vouches for the
creator). Pass ``"factory"`` for anything created from unauthenticated input.
Nothing to do otherwise.

.. code-block:: python

   # Before: nothing recorded how the actor was created
   ActorInterface.create(creator=email, config=config, hooks=app.hooks)

   # From 3.16: same call, marker "app"; say so for unauthenticated input
   ActorInterface.create(
       creator=email, config=config, hooks=app.hooks, auth_method="factory"
   )

The MCP OAuth server
--------------------

``_get_or_create_actor_for_email`` now delegates to the provider's authenticator,
so the adoption rule applies to MCP sign-ins. **Behavior change:** MCP sign-ins
write ``oauth_provider`` on every sign-in, and a new actor gets ``created_at``,
``oauth_provider``, ``email`` and the marker, as the other paths always did.

Closing the factory
-------------------

.. code-block:: python

   app = ActingWebApp(...).with_oauth(...).with_open_factory(False)

``POST /`` then answers ``403`` with ``{"error": true, "status_code": 403,
"message": "Actor creation is disabled on this server (with_open_factory); ..."}``
(the error page for a form), and the existing-creator form redirect, which told
anyone which actor id belongs to an address, is closed with it. This deviates
from the protocol's mandatory factory, so the factory stays open unless you
call it; a basic-auth deployment that needs the factory form login keeps it
open. A closed factory still renders the ``GET /`` page and its form, whose
submit gets the 403; replace the template if that page should not offer one.
The reference demo app reads ``OPEN_FACTORY`` (default ``true``, so the
quickstart curl works).

Hooks
-----

* ``actor_adopted`` is new; see :doc:`../reference/hooks-reference`. It may fire
  more than once for one actor.
* ``actor_deleted`` and ``actor_deleted_complete`` also fire when a sign-in
  replaces a factory-created actor, with ``reason="replaced_at_adoption"`` and
  ``replaced_by_identifier``. A hook that mails "your account was deleted" or
  cancels billing should check ``reason``. A replacement that fails mid-wipe is
  re-run by the next sign-in, so they may fire more than once for one old
  actor. **Check** that both hooks accept ``**kwargs``: one written as
  ``def on_deleted(actor):`` raises ``TypeError`` on these keyword arguments,
  which is logged and skipped, so its cleanup never runs for a replaced actor.
* ``auth_method`` is written before ``actor_created`` fires; the other
  post-create fields still are not set at hook time.

``Actor.modify``
----------------

``Actor.modify(creator=None, passphrase=None)`` now takes a passphrase and
returns the backend result. DynamoDB raises on a failed save and PostgreSQL
returns ``False``; PostgreSQL also reports a zero-row update as failure. Code
that ignored the return value is unaffected. ``Actor.delete`` returns ``True``
when the backend reported no fault removing the actor row (it returned
``None``).

Changing the creator over HTTP
------------------------------

``PUT /<id>/trust/trustee`` with a new ``creator`` marks the actor
``creator_changed``, which is unvouched: the first sign-in that proves the new
address cleans it in place. Two values keep the marker: ``trustee`` (the
protocol's handoff) and the actor's own stored ``email``, so handing an actor
to its trustee and back to its owner changes nothing. A ``factory`` actor keeps
``factory``: it is still replaced at the first sign-in, not cleaned. With
``force_email_prop_as_creator`` on and a stored email, a ``creator`` other than
those two answers ``400``: the creator is pinned to that email.

The endpoint answers ``500`` and changes nothing (``trustee_root`` included)
when it cannot read the actor's ``_internal`` bucket, when the marker cannot
be written, or when the creator change itself fails. In the last case the
previous marker is restored once a fresh read shows the creator unchanged,
and only while the marker still reads ``creator_changed``; when that read
fails the actor stays ``creator_changed``. A creator change that loses a
race answers ``409`` when another request changed the creator meanwhile,
``404`` when the actor was deleted, and succeeds when the stored creator is
already the one asked for (this request's own write, whose answer was
lost). A reserved value (``#…``, ``#dup-``, ``system``, ``oauth2-system``)
answers ``400``.

A vouch is bound to the address it proved: every vouched marker is written
with that address (``vouched_creator``), and an actor whose creator changed
since reads as unvouched whatever order concurrent writes land in. An actor
vouched before 3.16 has no recorded address and is judged by its marker
alone until a sign-in or ``actingweb-mark-actors-vouched`` records one. The
emailed verification link proves only the address it was sent to: an actor
whose creator changed since the link was sent answers ``409`` and the link
stays unused. A link sent before the upgrade carries no recorded address
and is checked against the actor's stored ``email``; an actor with neither
answers ``409`` too, and the user signs in again for a new link.

**Behavior change, with or without the flag:** a ``modify`` through a stale
handle (another process renamed the actor since it was loaded) returns
False on both backends. On PostgreSQL this covers a creator change; on
DynamoDB also a password change, a handle whose actor was deleted, and a
rename through a handle loaded before a password rotation.

``ActorInterface.modify_creator()`` does not unvouch by default: the
application vouches for the address it passes. A route of your own that
passes user input to it should ask for the endpoint's rules::

    actor.modify_creator(new_address, unvouch=True)

Fault contract
--------------

Before 3.16 a database fault usually read like an answer: PostgreSQL caught
it and returned ``None``, ``[]`` or ``False``; DynamoDB did the same on most
single-row reads and raised on list reads. A caller could not tell "no such
trust" from "the read failed", and eleven callers acted on the guess: they
issued a new trust secret, overwrote a permission override, created a
duplicate actor, deleted an actor without notifying its peers, reset an open
circuit breaker. In 3.16 the decision reads raise, and those callers stop.

**What raises now.** On both backends, every single-row ``get``, every list
``fetch``, ``get_by_creator``, ``get_bucket``, ``get_attr``, the reverse
lookups and ``get_attr_strict`` raise ``actingweb.db.exceptions.DbError`` on
a fault. Writes and deletes raise too, and a delete through a loaded handle
answers ``True`` when the row is gone, including a row that was already
absent. Conditional deletes keep "``True`` only if this call removed it".
Pass ``strict=False`` to a read to get the old folded answer; only display
reads should.

**Public APIs that raise ``DbError`` on a fault:**

- ``Attributes.get_bucket()`` and ``get_attr()`` (``strict=False`` folds);
  ``actor.store`` (``InternalStore``) still never raises on a read and keeps
  ``loaded`` as its signal;
- ``Actor`` lookups (``Actor(actor_id=...)``, ``get_from_creator``,
  ``get_trust_relationship(s)``, ``get_subscriptions``, ``get_peer_trustee``)
  and ``Actor.delete``, which now reads its trusts and subscriptions before
  removing anything;
- the ``ActorInterface`` property, trust and subscription accessors built on
  them, and the property list container (``len()``, ``[]`` and iteration on
  ``actor.property_lists``), which no longer reads a fault as an empty list;
- the OAuth2 sign-in lookup and adoption, the SPA token check and the
  permission stores.

**What the HTTP layer does.** Both integrations register an app-level
handler: a ``DbError`` that reaches Flask or FastAPI, from a library route or
from your own route, answers ``503`` with ``Retry-After: 5`` and
``{"error": "temporarily_unavailable", "message": "Service temporarily
unavailable"}``. The exception text is logged, never sent. A sign-in that
hits a fault answers 503 too, not a failed login, and a token-store fault no
longer signs a SPA user out. ``CreatorTaken`` (a ``DbError`` subclass,
raised under ``with_unique_creator()``, see `Creator uniqueness`_) answers
``409``.

A backend error a retry cannot fix (a validation, size or constraint error,
such as an item over DynamoDB's 400 KB limit) answers ``500`` with
``{"error": "internal_error"}`` and no ``Retry-After``.

**Hooks.** The hook runners let a ``DbError`` through. A hook whose own
store read faults (an ``oauth_success`` allowlist kept in an attribute
bucket, a property hook that reads another property) fails the request with
503. Before 3.16 the runner logged the exception and carried on with "no
answer", which ``oauth_success`` treated as "accepted". The notifications
fired after the work committed (``actor_created``, ``actor_adopted``,
``actor_deleted_complete``, ``trust_approved``) still log a fault and let the
request succeed.

**Subscription callbacks.** A callback whose storage write faults answers
503. The publisher does not retry a callback (the protocol's delivery is
at-most-once); the diff stays on the publisher and comes back through a poll
or a gap resync, which runs the handler again. Once its handlers have run, a
fault recording the callback's sequence is logged and the callback answers
as processed, so ``subscription_data_hook`` handlers are not run twice for
it. The next callback then sees a gap, which the gap timeout resyncs.

**Subscription sequence numbers.** As a publisher, the library allocates
each diff's sequence number with one atomic update, so two concurrent
changes to one subscription get two numbers (before, both could read N and
write N + 1: PostgreSQL then rejected the second diff, DynamoDB overwrote the
first). A number whose diff could not be stored is no longer handed out
again; it stays a gap, which the subscriber detects at the next diff and
recovers from by polling or resyncing. A subscriber skipped on a store fault
gets a gap the same way. When the sequence row itself cannot be reached, no
gap can be made and the diff is lost; only a periodic poll recovers it. Both
backends refuse a diff whose number already has one. Upgrade every worker
before the new ones publish diffs: a 3.15 worker still writes the sequence as
``previous + 1`` and can move it back under a 3.16 one.

**Resuming suspended subscriptions.** ``resume_subscriptions()`` reads the
subscribers before it removes the suspension, and if a resync faults it puts
the suspension back and raises ``DbError`` (503), so the call can be retried
without losing the changes made while suspended. A permanent store error for
one subscriber and a resync that fails over HTTP do not put it back; check
the returned count against the number of subscribers.

**Consumer code to check:**

- An ``except Exception`` that treats a failed read as "absent" and then
  creates or deletes: re-raise ``DbError`` ahead of it.
- A custom route that should degrade instead of failing: catch ``DbError``
  and render what you have, or read with ``strict=False``.
- Code that checked ``store.loaded`` after ``Attributes.get_bucket()``: the
  read raises now; pass ``strict=False`` to keep checking ``loaded``.
- A hook that must degrade instead of failing the request on a fault: catch
  ``DbError`` inside the hook.

Custom database backends
------------------------

A backend must live inside ``actingweb.db`` and follow the contract the
module docstring of ``actingweb.db.protocols`` states:

- accept ``*, strict: bool = True`` on every ``get`` (except
  ``DbProperty.get``, which takes none and always raises), ``fetch`` and
  ``get_bucket``, and ``consistent`` and ``ids_only`` on
  ``DbActor.get_by_creator``;
- raise ``DbError`` on a fault (``raise DbError(op) from e``), and answer it
  as absence only when ``strict=False``;
- answer ``True`` from a delete through a loaded handle when the row is gone,
  absent rows included;
- keep ``delete_attr_conditional`` and ``conditional_update_attr`` answering
  ``True`` only when that call changed the row;
- implement ``DbSubscription.increment_seq(actor_id=None, peerid=None,
  subid=None)`` as one atomic update that returns the new sequence number
  (None when the row is gone). The library no longer writes ``previous + 1``
  through ``modify(seqnr=...)``, which let two concurrent changes share a
  number.

A backend without ``strict`` fails with ``TypeError`` at its first call; one
without ``increment_seq`` fails with ``AttributeError`` at its first diff.

For creator uniqueness, ``DbActor`` must also:

- accept a keyword-only ``unique_creator: bool = False`` in its constructor
  (``actingweb.db.get_actor`` passes ``config.unique_creator``; without it
  construction fails with ``TypeError``) and a keyword-only
  ``replace_holder`` on ``create``;
- with the flag set, raise ``CreatorTaken`` from ``create`` and ``modify``
  when another actor holds a non-exempt creator (the rules are in
  ``actingweb.db.creator_rules``);
- implement ``replace_creator_holder(old_id, *, actor_id, creator,
  passphrase)``, creating ``actor_id`` and moving the creator from
  ``old_id`` in one atomic step (``CreatorTaken`` when ``old_id`` no longer
  holds it), ``get_creator_holder(creator, *, strict=True)``, a
  consistent read of the one holder, and ``release_stale_creator(creator,
  actor_id)``, which removes a record naming an actor that is gone or holds
  another creator and returns whether it did (a backend whose uniqueness
  lives on the actor row, as PostgreSQL's does, returns False).

Creator uniqueness
------------------

Before 3.16 ``with_unique_creator()`` made ``Actor.create`` list the
creator's actors and refuse when it found one. Two concurrent sign-ins or
factory posts could both pass that check, a creator change was never
checked, and a factory post with the existing actor's passphrase got that
actor back. In 3.16 the database holds one actor per creator:

- **DynamoDB:** a ``<prefix>_creators`` table, one item per held creator.
  An actor create puts the actor and its record in one
  ``TransactWriteItems``; a creator change updates the actor and puts the
  new record in one. The old record (after a delete or a creator change) is
  then removed by a separate conditional delete, only if it still names
  the actor; a fault there is logged and leaves a record that ``report``
  lists. The actor table and its scans are unchanged.
- **PostgreSQL:** the partial unique index ``ux_actors_creator`` on
  ``actors (creator)`` for every value other than ``trustee``, ``creator``
  and the empty string. It is built by the command below, not by an Alembic
  migration (a migration would fail on every deployment with duplicates),
  and ``alembic revision --autogenerate`` ignores it.

``trustee``, ``creator`` and the empty creator stay shared. Addresses (values
with ``@``) are lowercased before they are stored; provider ids such as
``apple:…`` compare exactly.

The flag stays **off by default** in 3.16 and turns on at the next major.

.. _Step 0:

**Step 0, for a deployment that runs the flag on.** Neither the index nor
the table can be switched on while actors share a creator, so in order,
with the application's environment (``DATABASE_BACKEND``, the database
settings, ``AWS_DB_PREFIX``, credentials).

**DynamoDB permissions.** If your IAM policy lists tables by name, add
``<prefix>_creators`` to the application's role (``GetItem``, ``PutItem``,
``UpdateItem``, ``DeleteItem``, and ``DescribeTable`` unless table
auto-creation is off) before step 4, plus ``ConditionCheckItem`` on the
actor table, and give the role that runs the command ``CreateTable`` and
``Scan`` on it as well. Without them the startup
check cannot read the table and the application refuses to start.

1. ``actingweb-unique-creators report`` lists actors sharing a creator
   (including addresses that differ only by case) and exits 1 if there are
   any.
2. ``actingweb-unique-creators resolve`` prints which actor of each group it
   keeps and how it renames the others; ``resolve --apply`` does it.
3. ``actingweb-unique-creators enable --apply`` creates and fills the
   DynamoDB table or builds the PostgreSQL index ``CONCURRENTLY`` (it
   refuses while duplicates remain).
4. Deploy 3.16.
5. ``actingweb-unique-creators enable --apply`` again: it records actors the
   old processes created during the deploy. Re-running it is safe.
6. ``actingweb-unique-creators report``. If it lists anything (an actor
   created in the window with a creator another actor holds, or a record
   left by a delete in an old process), run ``resolve --apply``, then
   ``enable --apply``.

Close the factory for the window with ``with_open_factory(False)`` if you
can. The application refuses to start with the flag on until step 3 has run
(``UniqueCreatorNotReady``); call ``ActingWebApp.check_ready()`` yourself if
you use neither integration. If the check cannot reach the database, the
application refuses to start as well (``UniqueCreatorNotReady``, naming the
fault): starting unchecked on DynamoDB, against an empty auto-created
``creators`` table, would let every existing user's next sign-in create a
second actor.

``report``, ``resolve --apply`` and ``enable --apply`` are safe to run
against live traffic with the flag on (steps 5 and 6): what they list as
damage is confirmed by a consistent read of the actor or record, and a
record they write commits only while its actor is as read, so an actor
created or renamed while they run is left alone. ``resolve`` points the
record at the actor it keeps before it renames the others, so a sign-in
during the run lands on the kept actor. ``enable`` lists a
creator recorded for another actor and carries on, and writes the
backfill-complete item only when it listed nothing. ``--creator`` is
refused for ``enable`` and ``disable``.

**Which actor ``resolve`` keeps.** The best by marker (vouched, then
unvouched, then ``factory``), then the oldest (PostgreSQL's ``created_at``;
on DynamoDB the ``created_at`` the OAuth sign-in stores, unknown ages last),
then the lowest id. A group with an actor whose marker cannot be read is
skipped and reported. ``resolve --keep <id>`` overrides the rule for that
id's group. The others are renamed to ``<creator>#dup-<hash>`` and their
stored ``email`` is cleared, so ``force_email_prop_as_creator`` cannot undo
the rename; nothing is deleted. **A renamed actor no longer opens with its
old creator** (basic auth, OAuth sign-in): choose the kept actor with
``--keep`` before ``enable``, or change creators with
``ActorInterface.modify_creator`` afterwards.

**Rolling back.** Turn the flag off and wait until every process that ran
with it has stopped (one still serving would find no holder for anybody and
create duplicates), then run
``actingweb-unique-creators disable --apply``. Re-running it finishes a run
that stopped part way. It drops the PostgreSQL
index, or deletes the DynamoDB backfill-complete item and every record (the
empty table can then be dropped by hand), so turning the flag on again
starts with Step 0 from the actors, not from records that went stale while
it was off. On PostgreSQL the index keeps answering ``CreatorTaken`` while
it exists, even with the flag off.

**What the flag changes once enabled:**

- A create or creator change for a creator another actor holds raises
  ``CreatorTaken``: ``ActorInterface.create`` and
  ``ActorInterface.modify_creator`` raise it,
  ``PUT /<id>/trust/trustee`` answers 409 and applies nothing else from the
  request, and a route of your own answers 409 through the app-level handler.
- The factory answers 403 "Creator already exists" for a held creator,
  whatever the passphrase. A client that relied on getting the existing
  actor back for its passphrase should keep the id and URL from the first
  201 and use basic auth on ``/<id>``, or sign in through OAuth.
- A sign-in that replaces a ``factory`` actor creates the successor first
  and moves the creator to it in the same backend step, then removes the
  squatter, so ``actor_created`` for the successor fires before
  ``actor_deleted`` for the squatter. There is no ranking of duplicates and
  no sibling sweep. If the squatter was renamed in the meantime the sign-in
  fails closed; if its deletion status cannot be read, it answers 503.
- Two concurrent first sign-ins for one identifier (two tabs, a retried
  callback) both end on the actor the first one created; one that finds
  that actor before its ``auth_method`` marker is readable (only rows an
  older process wrote) answers 409 instead.
- A record whose actor is gone, or holds another creator now (left by a
  release that faulted, or by an old process during the rollout), is
  removed by the next sign-in for that creator, which then creates the
  owner's actor; the stale record never signs anyone in to that actor.
- A sign-in that loses the swap to a concurrent sign-in for the same
  squatter ends on the winner's successor.
- A DynamoDB create whose answer was lost after the transaction committed
  answers 503 although the actor exists; a retry then gets
  ``CreatorTaken``. ``report`` does not flag it: sign in, or look the
  creator up, to reach the actor.
- Two applications sharing one actor table can no longer both bootstrap
  their system actors (``system``, ``oauth2-system``).

- On DynamoDB an actor create, delete or creator change costs about 4-6
  write units instead of 1 (a transaction, and the conditional release of
  the old record). Only opted-in tables pay this.

**Scripts that write actors directly.** ``actingweb_mcp``'s
``scripts/restore_actor.py`` writes through ``DbActor``: either create
through ``Actor.create`` with the flag on, or run ``resolve --apply`` and
``enable --apply`` after it. ``report`` finds what such a script leaves.

**Consumer code to check:**

- Catch ``CreatorTaken`` from ``ActorInterface.create`` and
  ``modify_creator`` where you create or rename on the user's behalf, or let
  the app-level handler answer 409. Test for it before ``DbError``: it is a
  subclass, but a conflict, not an outage.
- A caller that relied on the factory returning the existing actor for a
  matching passphrase.
- Monitoring: ``actingweb-unique-creators report`` exits 1 when it finds
  anything, and 2 when the store cannot be read.

SPA ``prompt``
--------------

``POST /oauth/spa/authorize`` accepts ``"prompt": "select_account"``. It is
additive: ``consent`` is always sent. Google receives ``select_account
consent``; GitHub and Apple ignore it. ``GET /oauth/spa/config`` lists
``prompt_values`` and a per-provider ``prompt_supported`` (as does
``/oauth/config``; ``GET /?format=json`` lists ``prompt_values`` only). Any other value
answers ``400``. See :doc:`../guides/spa-authentication`.

Spanned list items
------------------

A property-list item is one storage row, so on DynamoDB an item cannot
exceed about 400 KB. Before 3.16 an oversized write failed with the untyped
``DbError("property write")``, and a consumer had to refuse large items with
its own rule. 3.16 adds two limits, ``list_item_span_threshold`` and
``list_item_max_bytes`` (``ActingWebApp.with_list_item_limits()``), and
spans a v2 item over the threshold across several rows. See
:doc:`../guides/property-lists` ("Items larger than one row") for the full
picture; what an upgrade needs:

- **Nothing changes shape in the actor's partition.** Existing rows keep
  their form, and a spanned item's body rows live in a separate side
  partition (``{actor_id}$aux``) that no dump or range read of the actor
  returns. A 380,000-byte item stays one row.
- **PostgreSQL is unchanged at its defaults** (no spanning, no ceiling). A
  deployment that develops on PostgreSQL and runs DynamoDB in production
  sets both limits in the app, so spanning happens in development too:

  .. code-block:: python

     app.with_list_item_limits(span_threshold=390_000, max_bytes=4 * 2**20)

- **Drop your own size rule and catch the typed error.** An item over
  ``list_item_max_bytes`` raises ``ListItemTooLargeError`` (a
  ``ValueError``, before any write); catch it ahead of generic
  ``ValueError`` handling. The REST handlers answer 413.
- **Size the ingress limit at your edge** (Flask ``MAX_CONTENT_LENGTH``, an
  ASGI body-limit middleware, a proxy's or gateway's body-size setting) to
  ``list_item_max_bytes`` plus room for the JSON around it. The library's
  limit is a storage bound, not an ingress guard.
- **Read bodies on demand.** ``items_with_handles(resolve=False)`` and
  ``to_list_from_rows(rows, resolve=False)`` skip spanned items' bodies
  (their slot holds ``UNRESOLVED``; the handle carries ``spanned`` and
  ``bytes``) and ``item_at(handle)`` reads one. A listing benefits only if
  title and metadata live outside the large item.
- **Diffs over the threshold are references.** A list diff whose blob would
  exceed the threshold carries ``"spanned": true`` and ``"bytes"`` instead
  of its values; the subscriber re-reads the list. A pre-3.16 subscriber
  answers ``unknown operation`` and stores nothing.
- **Rolling deploys.** Until every process runs 3.16, a pre-3.16 reader sees
  a spanned item as an envelope dict, a pre-3.16 ``clear()``/``delete()``
  leaves its bodies for the aged sweep, and a pre-3.16 actor delete leaves
  the side partition for ``actingweb-verify-orphans`` to report. The sweep
  tooling ships in the same release as the writer, so deploy 3.16
  everywhere before raising any client's size limit.
- **Refusals.** ``downgrade_to_v1`` refuses a list holding spanned items,
  ``migrate_to_v2()`` refuses a v1 list holding a dict item whose first key
  is ``__aw_env`` (``reason="envelope-shaped item"``), ``append`` and the
  other writers refuse such an item, and new list names may not contain
  ``$``.
- **Actor ids.** ``Actor.create`` and ``ActorInterface.create`` refuse a
  caller-supplied ``actor_id`` containing ``$`` or longer than 251
  characters (``ValueError``, before any write). Generated ids are 32 hex
  characters and unaffected. An existing actor whose id already holds a
  ``$`` (possible only through a consumer's own ids) keeps working, except
  that a spanning write on it raises ``ValueError`` before anything is
  written. **Audit before deploying** if your application supplies its own
  actor ids: look for any id containing ``$``. An actor whose id is another
  actor's id plus ``$aux`` would share that actor's side partition; 3.16
  detects it, logs an ERROR and skips the sweep when the other actor is
  deleted, but rename it.
- **Pre-3.16 items shaped like an envelope.** Only a stored value whose
  first key is ``__aw_env`` with exactly the value ``1`` is read as a
  storage envelope; any other value, including a pre-3.16 dict item
  ``{"__aw_env": "x", ...}``, reads as the plain item it is and is never
  removed by the sweep. A pre-3.16 v2 item ``{"__aw_env": 1, "v": ...}`` is
  read as an envelope (its ``v``). New writes refuse dict items carrying the
  key, and ``migrate_to_v2`` refuses them in v1 lists. If your items could
  carry that key with the value ``1``, check before deploying.
- **REST permission errors deny.** The REST property handlers answer 403
  when the permission evaluator raises, instead of falling back to the
  legacy ``access`` table (which allowed ``friend``, ``partner`` and
  ``admin`` every property method). A database fault still answers 503.
- **Three lifecycles.** A list's ``delete()`` reaps its side-partition rows;
  an actor delete reaps its partition and its side partition; anything else
  (a crash between bodies and head, a failed best-effort cleanup) waits for
  ``actingweb-verify-property-lists --repair --sweep-spans``, which removes
  orphan generations older than an hour. The default ``verify()`` does not
  count leaked bodies; ``verify(spans=True)`` does.
- **A broken span answers 409.** A spanned item whose body rows are missing
  raises ``ListItemSpanError`` (a ``ListCorruptionError``); the 409's
  ``remedy`` names ``--sweep-spans`` or ``delete_by_handle()``, and its
  ``detail`` carries the item's rank.
- **Limits.** ``list_item_max_bytes`` may be at most 9,999 times
  ``list_item_span_threshold`` (the most body rows a span names); a pair
  outside that raises ``ValueError`` where it is set.


What stays the same
===================

* A provider access token or ``oauth_token`` cookie matched by email in
  ``auth.py`` does not adopt.
* Sibling actors that share a creator (``unique_creator`` off) and are not
  marked ``factory`` are not touched until a sign-in resolves to one: the rule
  acts on that actor. ``factory`` siblings are deleted by any sign-in that
  proves the address (item 2).
* A vouched actor that carries a deletion tombstone (a ``DELETE /<id>`` that
  stalled before its wipe) is returned to the sign-in as it is, as before.
* With ``unique_creator`` off, two concurrent first sign-ins may both run the
  rule; ``actor_adopted`` may fire twice. A second replacement reuses the
  successor the first one already created when it can read it, which narrows
  the race to two adjacent statements; it does not close it. With the flag on
  the database refuses the second create.
* Properties a squatter prefilled on a cleaned-in-place actor are reported,
  not removed.
* ``devtest`` must be off in production: it lets a caller rewrite ``_internal``,
  including ``auth_method``.
