# Iterations: What 4.0.0rc1 takes from its first consumer's read

## 2026-11-20, after verification (thoughts/verifications/2026-11-20-emm-4-0-adoption-findings.md)

1. **[Verification fix] The default sign-in page signs in again with a provider** — the email form shows whenever a provider is configured or the factory is open; one helper builds the page's values for the handler and both integrations' fallbacks, so Flask's `/` and `/login` get the provider buttons too (`actingweb/handlers/factory.py` `sign_in_page_values`, `actingweb/templates/aw-root-factory.html`, `actingweb/interface/integrations/flask_integration.py`, `fastapi_integration.py`, `tests/test_factory_open_switch.py`). Why: verification issue 1 (High): with a provider a form POST is a sign-in redirect, and Flask's default page was left with no way in. AC: AC-47 restated. Spec: delta amended.
2. **[Verification fix] A trust type registered before the start no longer crashes a fresh DynamoDB store** — a system actor (`system`, `oauth2-system`) created before the store is enabled is written without a creator record, as 3.15.1 writes it; the enable records it (`actingweb/db/dynamodb/actor.py` `_system_actor_before_enable`, `tests/integration/test_unique_creator_empty_store.py::test_a_trust_type_registered_before_the_start_on_a_fresh_store`). Why: verification issue 17 (High, from the consumer's run): `add_trust_type()` at import created the system actor, which was refused while the creators table was missing. AC: AC-13 extended (the test). Spec: delta amended.
3. **[Verification fix] A newer list layout fails its own entry in the default properties listing** — the default and `short` formats catch `ListItemNewerFormatError` per list and emit the marker the `full` and `metadata` formats already emit (`actingweb/handlers/properties.py`, `tests/test_list_newer_format_http.py::test_a_newer_list_layout_fails_its_own_entry_in_the_listing`). Why: verification issue 2 (Medium): one such list turned the whole listing (and a subscriber's baseline) into 409. AC: AC-25 extended (the test). Spec: none.
4. **[Verification fix] A failure after the self-enable's marker removes the marker** — the late scan and its records run under one guard that deletes the backfill-complete item on any exception (CRITICAL if that delete fails) before re-raising (`actingweb/maintenance/unique_creators.py` `enable_empty_store`, `tests/integration/test_unique_creator_empty_store.py::test_a_fault_after_the_marker_removes_it`). Why: verification issue 3 (Medium): a fault there left "complete" over an unrecorded actor and the retried start passed. AC: AC-50 extended (the test). Spec: none (the delta's "recorded, or the start is refused" now holds on a fault).
5. **[Verification fix] `check-ready` reads only a missing table as empty** — a denied permission or any other error from the empty, marker and lookup probes makes the gate unreadable (exit 2) instead of "ready at first start" (`actingweb/maintenance/check_ready.py` `_missing_table`, `tests/test_check_ready_command.py::test_a_denied_permission_is_not_an_empty_store`). Why: verification issue 4 (Medium): an operator role without Scan got exit 0 on a populated store. AC: AC-11 extended (the test). Spec: none (the delta's "never treats a missing table … as an empty store" decision is unchanged).
6. **[Verification fix] `check-ready`'s lookup gate applies the start's own test** — "ready at first start" for reverse lookup now means no actor has a property row (`properties_table_empty`), as `property_lookup.settle` decides, not "no user actors" (`actingweb/maintenance/check_ready.py` `_properties_empty`, `tests/test_check_ready_command.py::test_the_lookup_gate_follows_the_properties_table`). Why: verification issue 5 (Medium): the command and the start disagreed on orphan rows and on actors without properties. AC: AC-11 extended (the test). Spec: none.
7. **[Decision changed] `actingweb-mark-actors-vouched` writes only with `--apply`** — without it the run is a dry run, as for every other writing command; `--dry-run` is still accepted, and the two are mutually exclusive (`actingweb/maintenance/mark_actors_vouched.py`, `tests/test_mark_actors_vouched.py::TestApplyFlag`, `tests/test_operator_command_store.py`, `docs/migration/v4.0.rst`, `docs/quickstart/deployment.rst`, `CHANGELOG.rst`, `scripts/live_pair.py`). Why: verification issue 18 (Medium, from the consumer's run, which marked 105 actors meaning a dry run); the command is new in 4.0, so no released caller depends on the old default. AC: AC-55 added. Spec: delta amended.
8. **[Verification fix] The AC-34 seed test drives the authenticated initialize through the seed's session** — it could not fail before: the update ran on a fresh handler with no session (`tests/test_mcp_client_info_cache.py::test_an_unauthenticated_seed_is_not_a_first_name`). Why: verification issue 13 (Low). AC: none. Spec: none.
9. **[Verification fix] A newer list layout's error no longer points at `delete()`** — the list-`format` case gets its own remedy ("neither repairs nor deletes"), the newer-item case keeps the `delete()` hint (`actingweb/list_core.py` `ListItemNewerFormatError`, `tests/test_property_list_newer_format.py::test_each_newer_case_names_its_own_remedy`; the test was written after the change). Why: verification issue 7 (Low). AC: none. Spec: none.
10. **[Verification fix] An attribute list with a damaged meta row can be deleted again** — `delete()` refuses only a newer layout; an unparsable meta row passes the check, as before 4.0 (`actingweb/list_core.py` `_refuse_newer_layout_only`, `actingweb/attribute_list.py`, `tests/test_property_list_newer_format.py::test_a_list_with_a_damaged_meta_row_can_still_be_deleted`). A property list's `delete()` refused a damaged meta row before 4.0 too (it dispatches on the row); left as it was. Why: verification issue 6 (Low; a regression for attribute lists). AC: none. Spec: delta amended.
11. **[Verification fix] The Spec Delta names `clear()` as the second escape for a newer item** — `clear()` empties the list, newer heads included, as its test asserts (plan Spec Delta, property-lists). Why: verification issue 8 (Low). AC: none. Spec: delta amended.

Accepted without code (owner's stop rule: Low findings need no code): issues 9 (a `plain` challenge or none under the opt-out through the application's own `complete_client_authorization`, rc1 behaviour), 10 (two first starts at once), 11 (credential errors retried at start-up), 12 (`clear()`'s `stored_not_notified` before any delete), 14 (the remaining loose assertions), 15 (a `Config` built directly with OAuth keeps the factory open; the builders are the documented form), 16 (type hints on four tests, matching their files).
12. **[Verification fix] Traceability references corrected** — stale line numbers (AC-6, AC-29, AC-37) and the AC-27 repair test named (plan Traceability). Why: verification Remaining Tasks. AC: none. Spec: none.
13. **[UX refinement] The guide says the reverse lookup does not share creator uniqueness's exemption** — one sentence under "Collisions" (`docs/migration/v4.0.rst`). Why: the consumer's second note (2026-11-20) met the collision of two default-creator actors on both its databases and asked for it as a known issue; the guide already named the case, not why the exemption does not help. AC: none. Spec: none.

## 2026-11-20, after verification (thoughts/verifications/2026-11-20-emm-4-0-adoption-findings-2.md)

14. **[Verification fix] The self-enable never removes another start's marker, and records late system actors** — the marker is written only if absent (an existing one is another first start's: accepted, left in place); the cleanup removes only this start's own marker, on `Exception` not `BaseException`; the late pass records system actors as well as users (`actingweb/maintenance/unique_creators.py` `enable_empty_store`, `tests/integration/test_unique_creator_empty_store.py::test_a_failing_enable_never_removes_another_starts_marker`, `::test_a_system_actor_written_during_the_enable_is_recorded`). Why: second verification issues 1, 5 and 9 (High, Medium, Low): iteration 4's unconditional delete could take down a store another start had enabled. AC: AC-50 extended. Spec: none.
15. **[Verification fix] The system-actor exemption covers PostgreSQL and only the exact system actors** — one rule, `is_system_actor(actor_id, creator)` (the two fixed ids with their own creators), used by both backends: before the store is enabled such an actor is written without a record (DynamoDB) or before the index exists (PostgreSQL), and the enable covers it; any other id with a system creator is refused as before (`actingweb/db/creator_rules.py`, `actingweb/db/dynamodb/actor.py`, `actingweb/db/postgresql/actor.py`, `tests/integration/test_unique_creator_empty_store.py::test_a_trust_type_registered_before_the_start_on_a_fresh_store` (now both backends), `::test_only_the_system_actors_own_ids_skip_the_record`). Why: second verification issues 2 (High: the consumer's crash was still there on PostgreSQL) and 4 (Medium). AC: AC-13 extended. Spec: delta amended.
16. **[Verification fix] A dry run of the marking says so, and every instruction to run it says `--apply`** — the summary of a run without `--apply` ends "(dry run: nothing written; re-run with --apply)"; the changelog's first-steps note and adoption entry, the guide's step and live-pair row, and the sweep's log line say `--apply` (`actingweb/maintenance/mark_actors_vouched.py`, `actingweb/maintenance/unique_creators.py`, `CHANGELOG.rst`, `docs/migration/v4.0.rst`, `tests/test_mark_actors_vouched.py::test_a_dry_run_says_so_in_its_summary`). Why: second verification issue 3 (High): a dry run printed `marked=105`, exit 0, exactly like a write. AC: AC-55 extended. Spec: none.
17. **[Verification fix] The sign-in page's email form follows the authenticator its POST uses, and one failing provider is left out alone** — `email_form` is true when the factory is open or the default authenticator (the one a form POST redirects through) is enabled; each provider's URL is built under its own guard (`actingweb/handlers/factory.py` `sign_in_page_values`, `tests/test_factory_open_switch.py::TestSignInPageValues`). Why: second verification issues 6 (Medium: a form whose POST would answer 403) and 7 (Low: one throwing provider removed every way in). AC: AC-47 extended. Spec: none.
18. **[Verification fix] `ListCore.delete()`'s comment says what passes** — only an attribute list deletes a list with an unparsable meta row (`actingweb/list_core.py`). Why: second verification issue 11 (Low). AC: none. Spec: none.

Accepted without code (Low): issue 8 (FastAPI with the web UI off already served the root template before this branch; it now carries the provider buttons too) and issue 10 (`check-ready` reads a missing properties table as empty; on DynamoDB the start creates it before the check, on PostgreSQL the attribute-lists gate already refuses with `alembic upgrade head`).
19. **[UX refinement] The default-creator collision is a named known issue in the guide** — a note under "Collisions": how factory actors without an address end up sharing an indexed value, that the start refuses, what to do before the upgrade, and why it is not suppressed (`docs/migration/v4.0.rst`). Why: the consumer asked (2026-11-20, third note) for it as a known issue; iteration 13's sentence did not make it findable. AC: none. Spec: none.

## 2026-11-20, after verification (thoughts/verifications/2026-11-20-emm-4-0-adoption-findings-3.md)

20. **[Verification fix] A start that finds another start's marker runs the late pass too** — it no longer trusts that the marker's writer finished: it records what was created since its first scan (idempotent), and if that fails it refuses with `EnableRefused` naming `enable --apply` (not a retryable fault, since a retried check would find the marker and pass), leaving the marker in place (`actingweb/maintenance/unique_creators.py` `enable_empty_store`, `tests/integration/test_unique_creator_empty_store.py::test_a_failing_enable_never_removes_another_starts_marker` (now expects the refusal), `::test_a_start_that_finds_the_marker_records_what_was_created_meanwhile`). Why: third verification issue 1 (Medium, operator-side). A start killed between its save and the end of its late pass still leaves "complete" unchecked (accepted). AC: AC-50 extended. Spec: updated (SRD-3).
21. **[UX refinement] The known-issue note names the second way out** — accepting the collision with `mark-complete --force` (`docs/migration/v4.0.rst`). Why: third verification issue 4 (Low). AC: none. Spec: none.

Accepted without code (Low, owner 2026-11-20): third verification issues 2 (a system actor saved after the late pass is unrecorded; `report` lists it) and 3 (the email form checks the default provider's `is_enabled()`, not its URL build).

## 2026-11-20, after the PR opened (#184; owner: take the unserialisable-value todo into 4.0)

22. **[New functionality] An attribute value `json` cannot encode is refused as `UnserialisableValue`** — every attribute write on both backends calls `require_json` first and raises `UnserialisableValue` (a `ValueError` and a `TypeError`, not a `DbError`), writing nothing; before, the encode failed inside the store call and read as `DbError` (503, `Retry-After`) (`actingweb/db/exceptions.py`, `actingweb/db/dynamodb/attribute.py`, `actingweb/db/postgresql/attribute.py`, `tests/test_unserialisable_value.py`, `CHANGELOG.rst`, `docs/migration/v4.0.rst`; the todo and its `INDEX.md` row deleted). Properties and list items were checked and do not raise on such a value. Why: the consumer's report (2026-11-19, verified then): a client that retries on 503 retried forever. AC: AC-56 added. Spec: property-lists updated (PLS-6).
