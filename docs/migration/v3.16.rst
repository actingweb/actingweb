===========================
Migrating to ActingWeb 3.16
===========================

.. warning::

   This guide shows the API **as it evolved across this migration**. Where
   a block demonstrates the *previous* pattern, it must not be copied into
   new code; see :doc:`../guides/index` for the current API.

Start here
==========

3.16 closes a squat on the actor factory, makes a database fault an error
instead of a guess, makes creator uniqueness (on by default) a guarantee the
database enforces, binds every peer to its own paths, and adds ``prompt``
to the SPA sign-in. Most applications need to check only the first three
items, item 11 and item 18.

.. warning::

   **An application does not start on 3.16 until you have run
   ``actingweb-unique-creators``,** because creator uniqueness is on by
   default (the demo application and ``actingweb_mcp`` already used it). Run
   `Step 0`_ against the production database before the deploy; the
   application otherwise raises ``UniqueCreatorNotReady`` from
   ``integrate_flask`` / ``integrate_fastapi``. A **fresh** deployment starts
   once (which creates the tables and stops), runs
   ``actingweb-unique-creators enable --apply``, and starts again; with no
   actors yet the refusal says so in one line. To keep the old behaviour, call
   ``with_unique_creator(False)``.

1. **An actor created before 3.16 with no marker is cleaned at its first
   sign-in after the upgrade.** That covers the factory, the email form,
   direct ``Actor.create`` calls and the MCP OAuth server; actors the provider
   sign-in buttons created already carry ``<provider>_oauth2`` and are left
   alone. Its passphrase is rotated and its trusts, subscriptions,
   sessions and registered OAuth2 clients are removed (MCP connectors must
   register and authorize again); its data is kept. Install 3.16 and run
   ``actingweb-mark-actors-vouched`` *before the application serves its first
   sign-in* to skip that for actors you know are legitimate. **An application
   whose users signed up through an MCP connector must run it:** the MCP OAuth
   server proved those addresses through the provider but never wrote a
   marker, so they are real accounts that would otherwise be cleaned.
2. **Actors created through ``POST /`` after the upgrade are replaced, not
   cleaned,** at the first sign-in that proves their address: new actor id,
   data gone. If your deployment creates actors through the factory and later
   signs the same users in with OAuth, create them with
   ``ActorInterface.create()`` instead, or close the factory. The same goes
   for the factory form with ``www_auth="oauth"``: the actor it creates is
   replaced at the OAuth callback that follows, so ``actor_created`` fires
   twice (and ``actor_deleted`` once) for one first login. A replacement also
   deletes the other ``factory`` actors with the same creator, and a sign-in to
   a vouched actor deletes the ``factory`` actors beside it (``actor_deleted``
   fires for each; at most 10 per sign-in, not counting the actor a
   replacement removes, the rest at later ones), and a lookup
   by creator among several that share it prefers a vouched actor, then any
   other unvouched one, and takes a ``factory`` actor last: an owner's actor
   from before 3.16 beside a squatter's is the one cleaned, with its data.
3. **An OAuth-only deployment should close the factory:**
   ``.with_open_factory(False)``.
4. Code calling ``Actor.create`` or ``ActorInterface.create`` directly needs
   no new argument for new ids: the new ``auth_method`` keyword defaults to
   ``"app"``. With a caller-supplied ``actor_id`` that is already taken,
   ``create`` now returns ``False`` (``ActorInterface.create`` raises)
   instead of ``True``. **A process that creates actors without
   ``integrate_*``** (a worker, a restore or import script, a test harness
   that builds ``Config()`` itself) must call ``check_ready()`` or run
   against a store where ``actingweb-unique-creators enable --apply`` has
   run, item 12 included: on a store without it, a fresh table prefix the
   library auto-created for instance, every create raises ``DbError``
   (see `Direct Actor.create and ActorInterface.create callers`_).
5. MCP sign-ins now write the same actor fields as the other paths.
6. A hook on ``actor_deleted`` or ``actor_deleted_complete`` may now see
   ``reason="replaced_at_adoption"``.
7. ``Actor.modify`` now takes a passphrase and returns the backend result;
   ``Actor.delete`` returns a bool.
8. SPA clients can ask for account selection with ``prompt``.
9. A custom database backend must accept ``strict`` on every ``get`` (except
   ``DbProperty.get``, which takes none and always raises), ``fetch`` and
   ``get_bucket``, raise ``DbError`` on a fault, and accept
   ``consistent`` and ``ids_only`` on ``DbActor.get_by_creator`` (see
   `Fault contract`_).
10. ``PUT /<id>/trust/trustee`` with a new ``creator`` unvouches the actor;
    with ``force_email_prop_as_creator`` on it refuses an address other than
    the stored email.
11. **A database fault now answers 503, not a guess.** Reads that decide
    something raise ``DbError`` on a throttle or timeout instead of reading
    as "not found", and both integrations answer it with ``503`` and
    ``Retry-After: 5``. Code that catches ``Exception`` around
    ``ActorInterface`` calls and treats it as "absent" should let
    ``DbError`` through (see `Fault contract`_).
12. **``with_unique_creator()`` is enforced** (see `Creator uniqueness`_):
    a second actor for a creator raises ``CreatorTaken`` (409; the factory
    keeps its 403), the factory no longer returns an existing actor for a
    matching passphrase, and the application refuses to start until the
    command has enabled enforcement.
13. The factory form redirects an address that has an actor to ``/login``,
    not to ``/<id>/www``, and creators beginning with ``#`` or containing
    ``#dup-``, and ``system`` and ``oauth2-system``, are refused with 400.
14. **Property-list items larger than one row now span** (see
    `Spanned list items`_): on DynamoDB a v2 list item over 390,000 encoded
    bytes is stored across several rows instead of failing, an item over
    4 MiB raises ``ListItemTooLargeError`` (413 over REST) before any write,
    and PostgreSQL is unchanged at its defaults. **Deploy 3.16 everywhere
    before any client stores a larger item**: a pre-3.16 reader sees a
    spanned item as an envelope dict. ``$`` is refused in new list names and
    in a caller-supplied actor id, and a list diff over the threshold is sent
    as a reference.
15. **A ``GET`` with ``?_method=`` refuses a cross-site request** (see
    `Cross-site requests`_): links to ``?_method=PUT|POST|DELETE`` work
    from the application's own pages, but a link on another site, or one
    opened from a mail or chat client, answers 403. A script that sends
    ``?_method=`` with the web UI's session cookie and no browser headers
    must send the real HTTP method. A peer's trust ``id`` and ``baseuri``
    must be plain shapes, and a custom template must not interpolate a
    value inside an inline event handler.
16. **``append_once(item, key=...)`` makes a create repeatable** (see
    `Idempotent appends`_). Nothing changes for code that does not call it,
    except that a v2 list's ``verify()`` report gains ``key_rows``,
    ``dangling_key_rows``, ``duplicate_keyed_items`` and
    ``unkeyed_keyed_items``. Deploy 3.16 everywhere before the first call.
17. **One reverse-lookup mechanism, and a startup check for it** (see
    `One reverse-lookup mechanism`_). The legacy ``property-index`` GSI path,
    the v1 lookup table, the PostgreSQL value scan and
    ``USE_PROPERTY_LOOKUP_TABLE`` are gone. A deployment whose properties hold
    data but whose indexed names were never backfilled does not start:
    ``check_ready()`` raises ``PropertyLookupNotReady`` naming
    ``actingweb-property-lookup backfill --apply``. An indexed property write
    whose lookup row cannot be written now fails with ``DbError`` (503).
    ``DbProperty`` and ``DbPropertyList`` require ``indexed_properties``.
18. **Callbacks are authenticated, and a peer reaches only its own paths**
    (see `Peer paths are bound to their peer`_). A ``/callbacks`` request
    without credentials answers 401; an access row admits only the method a
    request performs; a peer's own subscription and trust row are admitted
    by the built-in ``owner`` rows, so a GET-only subscriber type needs no
    new rows. A trust request for a peer that already has a
    trust is a re-pair that must carry the current secret. After every
    instance runs 3.16, run ``actingweb-peer-state report`` (then ``prune
    --apply``) and restart.


What changed and why
====================

The factory squat
-----------------

``POST /`` creates an actor for any address nobody has claimed, with a
passphrase of the caller's choosing, and needs no authentication. Before 3.16
the address owner's first OAuth login adopted that actor as theirs with the
squatter's credentials still live: the passphrase, any trust relationship made
with it (including an ``admin`` trust to the squatter's own actor with a secret
the squatter chose), any subscription, and any property the squatter prefilled.

From 3.16 every creation path records how the actor came to exist in
``auth_method`` (see :doc:`../guides/authentication`), and a sign-in that proves
an address over an actor nobody vouched for no longer inherits it. The protocol
mandates the factory, so it stays; the fix is that a self-asserted ``creator``
can no longer be inherited as a verified identity.

Two populations, two behaviours
-------------------------------

.. list-table::
   :header-rows: 1

   * - The unvouched actor
     - At the first address proof
     - Data
     - Actor id
   * - Created before 3.16 with no marker (any path but the provider
       sign-in buttons, the MCP OAuth server included),
       ``email_unverified``,
       ``creator_changed`` (its creator was set through
       ``PUT /<id>/trust/trustee``), or ``email_verified == "false"``
     - **Cleaned in place**: passphrase rotated; every trust, subscription,
       SPA session, MCP token and registered OAuth2 client removed; stored
       provider tokens and ``trustee_root`` cleared; marked
       vouched
     - kept
     - unchanged
   * - Created through ``POST /`` after the upgrade (``factory``)
     - **Replaced**: deleted through the tested wipe and recreated
     - gone
     - new

*Cleaned in place* is for actors that may belong to their legitimate creator:
a pre-3.16 deployment's factory-then-OAuth users, and the self-asserted email
form's users, who by design hold a two-week session and real data before they
verify. Properties a squatter prefilled are **reported, not removed**: the
``actor_adopted`` hook carries their names so the application can inspect them.

An *address proof* is a provider login or the emailed verification link. The
link also runs the in-place rule before marking the address verified, so a
squatter whose provider profile carries the victim's address cannot keep a
session through a phished "verify your email" click. A user who verifies by
link therefore gets a new passphrase and has their sessions revoked: the
application should send them to sign in again after the click.

A user whose provider supplies no verified address reaches the free-text email
form at every sign-in, and that form answers ``409`` for an address that
already has an actor (as before 3.16). Such a user can sign in again once the
provider supplies the address, for example after verifying it at GitHub. The
verification click only moves the sign-out earlier: the session used to last
until it expired. The same ``409`` meets such a user whenever someone else
created an actor for their address through the open factory first, which is
one more reason for an OAuth deployment to close it.

No request leaves the process during either: the peer URLs on an unvouched
actor were chosen by whoever created it, so the wipe skips the remote
``DELETE`` calls and keeps every local cleanup. If the wipe cannot be
confirmed the sign-in fails closed (an ERROR is logged and the actor stays
unvouched), and the next sign-in retries. The status the client sees is
``502`` on ``/oauth/callback`` and ``500`` on the SPA authorize and token
endpoints and on the verification link.

Marking actors you trust before the first sign-in
-------------------------------------------------

An actor that already holds legitimate relationships should not be cleaned at
its next login. The tool ships with the library and needs 3.16: install the
upgrade, then mark the actors before the application serves its first sign-in,
with the application's own environment:

.. code-block:: bash

   actingweb-mark-actors-vouched --dry-run
   actingweb-mark-actors-vouched --marker operator
   actingweb-mark-actors-vouched --creator alice@example.com

(``python -m actingweb.maintenance.mark_actors_vouched`` and, in a source
checkout, ``scripts/mark_actors_vouched.py`` run the same code.)

The tool writes ``auth_method`` on actors that have none and leaves every
actor that already carries a marker alone. It resumes with
``--start-after <actor id>`` and scans the whole actor table (maintenance, not
a serving path). The scan is streamed and keeps only each matching actor's id
and creator, about 220 MB per million actors, before it processes them in
sorted id order. On DynamoDB it is strongly consistent, because the tool
writes back the creator it read, so it costs twice the read units of an
eventual scan; ``--rate-limit <units per second>`` caps it (ignored on
PostgreSQL). ``--include-factory`` also re-marks ``factory`` actors, for a
deployment that kept the factory open after upgrading and wants to vouch for
what it created; run that while no sign-in is served, since a sign-in replacing
one of those actors (or a sibling of it) deletes it whichever is first. A value that does not vouch (``factory``,
``email_unverified``, ``creator_changed``) is refused as ``--marker``. Every
actor the **MCP OAuth server** created before 3.16 is unmarked too, and the
same tool covers them.

Reading the output. The last line reports:

``scanned``
   Actors considered (after ``--creator`` and ``--start-after``).
``marked``
   Marker written and read back (or, with ``--dry-run``, would be).
``skipped``
   Already carried a marker; not touched.
``pending``
   Marked, but their email verification is still pending
   (``email_verified == "false"``). They stay unvouched and are cleaned at
   the sign-in that proves the address.
``errors``
   The marker could not be read or the write did not read back. Re-run;
   actors already marked are skipped.

A ``progress:`` line every 100 actors, and the closing
``last actor handled: <id>`` line, give the value for ``--start-after`` if the
run is interrupted. Once an actor has errored they say to re-run without
``--start-after`` instead: the actors that errored sort before that id.
Exit codes: ``0`` every actor was handled, ``1`` at least one error, ``2`` the
actor list itself could not be read and nothing was scanned (not a report of
zero actors), or an argument was refused, such as a ``--marker`` that does
not vouch; the message says which.

A cleaned-in-place actor's passphrase changes, so anything that stored the
old one must read the new one from ``GET /<actor_id>`` with the session token
(``Accept: application/json``).

Direct ``Actor.create`` and ``ActorInterface.create`` callers
-------------------------------------------------------------

Both take ``auth_method`` (default ``"app"``: the application vouches for the
creator). Pass ``"factory"`` for anything created from unauthenticated input.

A process that creates actors without ``integrate_*`` (a worker, a script, a
test harness that builds ``Config()`` directly) must also call
``ActingWebApp.check_ready()`` or run against a store where
``actingweb-unique-creators enable --apply`` has run. The ``DbActor``
constructor no longer creates the DynamoDB ``<prefix>_creators`` table, and
on PostgreSQL the first enforced create or creator change checks for
``ux_actors_creator``.
Without it, with uniqueness on and ``enable --apply`` not yet run, every actor create and creator change (a rename, a holder replacement) for a non-exempt creator, including the OAuth2 system actor bootstrap, raises ``DbError`` (``database error during actor create``, or ``actor modify`` and ``actor replace holder`` for the changes; 503 through the integrations, and retrying does not clear it) on both backends. Run ``actingweb-unique-creators enable --apply`` first, or call ``check_ready()``, which names the command.

.. code-block:: python

   # Before: nothing recorded how the actor was created
   ActorInterface.create(creator=email, config=config, hooks=app.hooks)

   # From 3.16: same call, marker "app"; say so for unauthenticated input
   ActorInterface.create(
       creator=email, config=config, hooks=app.hooks, auth_method="factory"
   )

The MCP OAuth server
--------------------

``_get_or_create_actor_for_email`` now delegates to the provider's authenticator,
so the adoption rule applies to MCP sign-ins. **Behavior change:** MCP sign-ins
write ``oauth_provider`` on every sign-in, and a new actor gets ``created_at``,
``oauth_provider``, ``email`` and the marker, as the other paths always did.

Closing the factory
-------------------

.. code-block:: python

   app = ActingWebApp(...).with_oauth(...).with_open_factory(False)

``POST /`` then answers ``403`` with ``{"error": true, "status_code": 403,
"message": "Actor creation is disabled on this server (with_open_factory); ..."}``
(the error page for a form), and the existing-creator form redirect, which told
anyone which actor id belongs to an address, is closed with it. This deviates
from the protocol's mandatory factory, so the factory stays open unless you
call it; a basic-auth deployment that needs the factory form login keeps it
open. A closed factory still renders the ``GET /`` page and its form, whose
submit gets the 403; replace the template if that page should not offer one.
The reference demo app reads ``OPEN_FACTORY`` (default ``true``, so the
quickstart curl works).

Hooks
-----

* ``actor_adopted`` is new; see :doc:`../reference/hooks-reference`. It may fire
  more than once for one actor.
* ``actor_deleted`` and ``actor_deleted_complete`` also fire when a sign-in
  replaces a factory-created actor, with ``reason="replaced_at_adoption"`` and
  ``replaced_by_identifier``. A hook that mails "your account was deleted" or
  cancels billing should check ``reason``. A replacement that fails mid-wipe is
  re-run by the next sign-in, so they may fire more than once for one old
  actor. **Check** that both hooks accept ``**kwargs``: one written as
  ``def on_deleted(actor):`` raises ``TypeError`` on these keyword arguments,
  which is logged and skipped, so its cleanup never runs for a replaced actor.
* ``auth_method`` is written before ``actor_created`` fires; the other
  post-create fields still are not set at hook time.

``Actor.modify``
----------------

``Actor.modify(creator=None, passphrase=None)`` now takes a passphrase and
returns the backend result. DynamoDB raises on a failed save and PostgreSQL
returns ``False``; PostgreSQL also reports a zero-row update as failure. Code
that ignored the return value is unaffected. ``Actor.delete`` returns ``True``
when the backend reported no fault removing the actor row (it returned
``None``).

Changing the creator over HTTP
------------------------------

``PUT /<id>/trust/trustee`` with a new ``creator`` marks the actor
``creator_changed``, which is unvouched: the first sign-in that proves the new
address cleans it in place. Two values keep the marker: ``trustee`` (the
protocol's handoff) and the actor's own stored ``email``, so handing an actor
to its trustee and back to its owner changes nothing. A ``factory`` actor keeps
``factory``: it is still replaced at the first sign-in, not cleaned. With
``force_email_prop_as_creator`` on and a stored email, a ``creator`` other than
those two answers ``400``: the creator is pinned to that email.

The endpoint answers ``500`` and changes nothing (``trustee_root`` included)
when it cannot read the actor's ``_internal`` bucket, when the marker cannot
be written, or when the creator change itself fails. In the last case the
previous marker is restored once a fresh read shows the creator unchanged,
and only while the marker still reads ``creator_changed``; when that read
fails the actor stays ``creator_changed``. A creator change that loses a
race answers ``409`` when another request changed the creator meanwhile,
``404`` when the actor was deleted, and succeeds when the stored creator is
already the one asked for (this request's own write, whose answer was
lost). A reserved value (``#…``, ``#dup-``, ``system``, ``oauth2-system``)
answers ``400``.

A vouch is bound to the address it proved: every vouched marker is written
with that address (``vouched_creator``), and an actor whose creator changed
since reads as unvouched whatever order concurrent writes land in. An actor
vouched before 3.16 has no recorded address and is judged by its marker
alone until a sign-in or ``actingweb-mark-actors-vouched`` records one. The
emailed verification link proves only the address it was sent to: an actor
whose creator changed since the link was sent answers ``409`` and the link
stays unused. A link sent before the upgrade carries no recorded address
and is checked against the actor's stored ``email``; an actor with neither
answers ``409`` too, and the user signs in again for a new link.

**Behavior change, with or without the flag:** a ``modify`` through a stale
handle (another process renamed the actor since it was loaded) returns
False on both backends. On PostgreSQL this covers a creator change; on
DynamoDB also a password change, a handle whose actor was deleted, and a
rename through a handle loaded before a password rotation.

``ActorInterface.modify_creator()`` does not unvouch by default: the
application vouches for the address it passes. It records the new address as
``vouched_creator_pending`` before the rename and moves it to
``vouched_creator`` after, so a sign-in during a rename finds the actor
vouched under either creator. Two concurrent renames of one actor share that
one pending value; serialise renames of one actor. With
``force_email_prop_as_creator`` on and a stored email, a rename moves the
stored email to the new address (before 3.16 the next load rewrote the
creator back to the old stored email), and a rename to a creator that is not
an address is refused. A route of your own that
passes user input to it should ask for the endpoint's rules::

    actor.modify_creator(new_address, unvouch=True)

Fault contract
--------------

Before 3.16 a database fault usually read like an answer: PostgreSQL caught
it and returned ``None``, ``[]`` or ``False``; DynamoDB did the same on most
single-row reads and raised on list reads. A caller could not tell "no such
trust" from "the read failed", and eleven callers acted on the guess: they
issued a new trust secret, overwrote a permission override, created a
duplicate actor, deleted an actor without notifying its peers, reset an open
circuit breaker. In 3.16 the decision reads raise, and those callers stop.

**What raises now.** On both backends, every single-row ``get``, every list
``fetch``, ``get_by_creator``, ``get_bucket``, ``get_attr``, the reverse
lookups and ``get_attr_strict`` raise ``actingweb.db.exceptions.DbError`` on
a fault. Writes and deletes raise too, and a delete through a loaded handle
answers ``True`` when the row is gone, including a row that was already
absent. Conditional deletes keep "``True`` only if this call removed it".
Pass ``strict=False`` to a read to get the old folded answer; only display
reads should.

**Public APIs that raise ``DbError`` on a fault:**

- ``Attributes.get_bucket()`` and ``get_attr()`` (``strict=False`` folds);
  ``actor.store`` (``InternalStore``) still never raises on a read and keeps
  ``loaded`` as its signal;
- ``Actor`` lookups (``Actor(actor_id=...)``, ``get_from_creator``,
  ``get_trust_relationship(s)``, ``get_subscriptions``, ``get_peer_trustee``)
  and ``Actor.delete``, which now reads its trusts and subscriptions before
  removing anything;
- the ``ActorInterface`` property, trust and subscription accessors built on
  them, and the property list container (``len()``, ``[]`` and iteration on
  ``actor.property_lists``), which no longer reads a fault as an empty list;
- the OAuth2 sign-in lookup and adoption, the SPA token check and the
  permission stores;
- ``SubscriptionManager.is_suspended()`` (and a custom backend's
  ``DbSubscriptionSuspension.is_suspended``), which answered ``False`` when
  the suspension could not be read. **Check:** in a background job, catch
  ``DbError`` and retry; do not treat it as "not suspended".

**What the HTTP layer does.** Both integrations register an app-level
handler: a ``DbError`` that reaches Flask or FastAPI, from a library route or
from your own route, answers ``503`` with ``Retry-After: 5`` and
``{"error": "temporarily_unavailable", "message": "Service temporarily
unavailable"}``. The exception text is logged, never sent. A sign-in that
hits a fault answers 503 too, not a failed login, and a token-store fault no
longer signs a SPA user out. ``CreatorTaken`` (a ``DbError`` subclass,
raised under ``with_unique_creator()``, see `Creator uniqueness`_) answers
``409``. ``DeletionInProgress`` (a ``DbError`` subclass: another request is
finishing the actor's deletion) answers ``503`` with ``Retry-After`` set to
the remaining seconds of that request's lease, not the fixed ``5``.

Two folds stay deliberately. A subscription callback's handlers run at most
once: once they have run, a fault recording the sequence is logged and the
callback answers as processed. The owner's sign-in removes the ``factory``
actors beside it as a best-effort sweep: a fault there is logged and the next
sign-in retries. A property write whose subscription diff cannot be
registered keeps the write and answers ``503`` (it used to succeed with the
diff lost); a client retrying a list ``append`` then writes a second item.

A backend error a retry cannot fix (a validation, size or constraint error,
such as an item over DynamoDB's 400 KB limit) answers ``500`` with
``{"error": "internal_error"}`` and no ``Retry-After``.

An exception counts as the fault only when it is the ``DbError`` or was raised
from one (``raise MyError(...) from e``). An error raised while a ``DbError``
was being handled, without ``from``, is a bug in that handler and answers
``500``. **Check:** in your own routes and hooks let the ``DbError`` itself
propagate (re-raise it, do not wrap it): the app-level handlers and the hook
runners match the type, so a wrapping exception answers ``500`` there, or in a
hook is logged and dropped, with or without ``from``.

``GET /?format=json`` answers ``Access-Control-Allow-Origin: *`` and no
``Access-Control-Allow-Credentials`` (it used to reflect the ``Origin`` with
credentials allowed). The document is public. **Check:** a cross-origin client
that sends credentials on this fetch (``credentials: 'include'``, axios
``withCredentials``) is refused by the browser now; drop them for this one
request.

**Hooks.** The hook runners let a ``DbError`` through. A hook whose own
store read faults (an ``oauth_success`` allowlist kept in an attribute
bucket, a property hook that reads another property) fails the request with
503. Before 3.16 the runner logged the exception and carried on with "no
answer", which ``oauth_success`` treated as "accepted". The notifications
fired after the work committed (``actor_created``, ``actor_adopted``,
``actor_deleted_complete``, ``trust_approved``) still log a fault and let the
request succeed.

**Subscription callbacks.** A callback whose storage write faults answers
503. The publisher does not retry a callback (the protocol's delivery is
at-most-once); the diff stays on the publisher and comes back through a poll
or a gap resync, which runs the handler again. Once its handlers have run, a
fault recording the callback's sequence is logged and the callback answers
as processed, so ``subscription_data_hook`` handlers are not run twice for
it. The next callback then sees a gap, which the gap timeout resyncs.

**Subscription sequence numbers.** As a publisher, the library allocates
each diff's sequence number with one atomic update, so two concurrent
changes to one subscription get two numbers (before, both could read N and
write N + 1: PostgreSQL then rejected the second diff, DynamoDB overwrote the
first). A number whose diff could not be stored is no longer handed out
again; it stays a gap, which the subscriber detects at the next diff and
recovers from by polling or resyncing. A subscriber skipped on a store fault
gets a gap the same way. When the sequence row itself cannot be reached, no
gap can be made and the diff is lost; only a periodic poll recovers it. Both
backends refuse a diff whose number already has one. Upgrade every worker
before the new ones publish diffs: a 3.15 worker still writes the sequence as
``previous + 1`` and can move it back under a 3.16 one.

**Resuming suspended subscriptions.** ``resume_subscriptions()`` reads the
subscribers before it removes the suspension, and if a resync faults it puts
the suspension back and raises ``DbError`` (503), so the call can be retried
without losing the changes made while suspended. A permanent store error for
one subscriber and a resync that fails over HTTP do not put it back; check
the returned count against the number of subscribers.

**Consumer code to check:**

- An ``except Exception`` that treats a failed read as "absent" and then
  creates or deletes: re-raise ``DbError`` ahead of it.
- A custom route that should degrade instead of failing: catch ``DbError``
  and render what you have, or read with ``strict=False``.
- Code that checked ``store.loaded`` after ``Attributes.get_bucket()``: the
  read raises now; pass ``strict=False`` to keep checking ``loaded``.
- A hook that must degrade instead of failing the request on a fault: catch
  ``DbError`` inside the hook.

Verified provider addresses
---------------------------

From 3.16 a provider's ``email`` is the sign-in identity, and is stored as
the actor's ``email``, only when the provider vouches for it: Google's
``verified_email`` or ``email_verified``, Apple's signed ``email_verified``,
or the GitHub address being in the token's verified list. Before, any
address the provider returned counted.

A user whose provider address was never verified therefore signs in to a new
provider-id actor (``google:<sub>``), or is asked for an address under
``force_email_prop_as_creator``, instead of the actor of that address. These
users cannot be found from stored data (the verified flag was never stored);
the sign-in logs a WARNING naming the provider and a redacted address.
**Check:** grep for ``not verified by the provider`` after the upgrade; to
re-link such a user to their old actor, verify their address yourself and
call ``ActorInterface.modify_creator()`` on the old actor (or merge the data
into the new one).

The emailed verification link now opens a page with a Confirm button; the
``POST`` verifies. A template that overrides ``aw-verify-email.html`` must
render the ``confirm`` state: a form that posts the ``verify_token`` value
as ``verify`` to ``action`` (``/oauth/email`` under the app's root). The
confirm issues no session; the user signs in afterwards. Its error states (an
invalid link, an expired sign-in session, a code that could not be sent)
carry ``redirect_url``, the app's root: render it as a way on, as the bundled
template does. The sign-in errors also carry ``title`` ("Sign-in expired",
"Sign in"), the page's heading in place of "Email verification".

A user whose provider has no verified address meets the email form again on
that later sign-in, and the form answers 409 for an address that has an
actor. Register ``email_sign_in_code_required`` (``func(actor, email, code,
expires_in)``) and send the code from it, as you send the verification link:
the form then asks for the code instead, and a correct one signs the page
in. A template overriding ``aw-oauth-email.html`` must render a
``code_challenge`` hidden field and a ``code`` input when
``code_challenge`` is set, and ``error`` beside them (a wrong code renders
the page again with it), plus a link to ``start_over_url`` (the app's root)
for a user whose code did not arrive. Raise from the hook only for a send
that failed: the form then answers 503, and the attempt still counts
against the five codes an hour. The page must be served over HTTPS: the
browser binding is a ``Secure`` ``__Host-`` cookie.

Stalled deletions
-----------------

A deletion that stopped part-way is finished by the next ``DELETE /<id>``,
by a sign-in to that actor, or by ``actingweb-deletions resume``. A
tombstone written before 3.16 records no reason, and a sign-in leaves a
vouched actor carrying one as it is. Every tombstone in a deployment
upgrading from 3.15 is of that kind. **Check:** after the upgrade run
``actingweb-deletions report`` with the application's environment; review
each ``legacy, review`` row, then ``resume ACTOR_ID --apply`` (the user wanted
the deletion) or ``clear ACTOR_ID --apply`` (a live actor whose create failed
to clear its tombstone). The command runs no application hooks and prints
the ids it finished, so run your own ``actor_deleted_complete`` cleanup for
them.

One reverse-lookup mechanism
----------------------------

3.13 made the lookup table the default and kept the older mechanisms as
fallbacks. 3.16 removes them.

**What was removed**

- The ``property-index`` GSI path on DynamoDB and the ``PropertyLegacy`` and
  ``PropertyIndex`` models; the v1 ``<prefix>_property_lookup`` table and its
  read fallback; the unindexed ``properties`` value scan on PostgreSQL.
- ``Config.use_lookup_table``, the ``USE_PROPERTY_LOOKUP_TABLE`` variable, the
  ``use_lookup_table`` constructor arguments, ``--legacy`` and
  ``--lookup-table`` on ``python -m actingweb.db.verify_tables``.
- ``ActingWebApp.with_legacy_property_index()`` stays as a tombstone that
  raises ``RuntimeError``, and ``Config`` refuses
  ``USE_PROPERTY_LOOKUP_TABLE=false`` and ``use_lookup_table=False`` at
  configure time. Both messages point here. A true value is ignored with a
  ``DeprecationWarning``. Delete the setting.

**The startup refusal**

``check_ready()`` (called by ``integrate_flask`` and ``integrate_fastapi``)
checks every configured indexed name. A name is ready when it carries a
backfill-complete marker, or when the properties table holds no row of an
actor's own (a fresh store marks itself on the first start; the library's
own ``_actingweb_*`` system-actor rows do not count). A name with data and no marker is
refused:

.. code-block:: text

    PropertyLookupNotReady: Reverse lookup is not ready for the indexed
    properties email: the properties table holds data but no backfill-complete
    marker covers them ... Run 'actingweb-property-lookup report', then
    'actingweb-property-lookup backfill --apply' ...

The check also records the indexed-name set on a passing start. A name that
was marked, dropped from ``with_indexed_properties()`` for a deploy and put
back is refused again, because values written while it was unindexed have no
lookup row. A store that cannot be read (missing lookup table, missing
permission, connection error) is refused with "could not be checked" naming
the table. ``check_ready()`` pre-warms DynamoDB tables first and reports this
and the creator-uniqueness refusal together in one ``StoreNotReady``; catch
``StoreNotReady`` (the base class of ``UniqueCreatorNotReady`` and
``PropertyLookupNotReady``) where you caught only ``UniqueCreatorNotReady``.
An application that never uses reverse lookup calls
``with_indexed_properties([])``. While the list is empty nothing is recorded,
so a name dropped that way and restored later is not caught: run
``actingweb-property-lookup backfill --apply`` for it first.

The recorded set is the last passing start's, whichever process made it (or
the union a ``backfill --apply`` or ``mark-complete --apply`` wrote), so
every process that shares a store must configure the same names. A process
with a non-empty indexed set that lacks a name (an old version during a rollout that adds one) writes that
name unindexed and records the smaller set; the refusal then names the
recorded set. Adding a name: deploy, run ``backfill --apply``, start the new
version, and run ``backfill --apply`` once more after the old version is gone;
until then an old-version start can make new starts refuse again
(``docs/quickstart/configuration.rst``).

**What to run**

With the application's environment (``DATABASE_BACKEND``, ``AWS_DB_PREFIX``,
``INDEXED_PROPERTIES``, credentials). The command reads the indexed names from
``INDEXED_PROPERTIES`` or the library default; if the application sets them with
``with_indexed_properties()``, pass the same names with ``--properties a,b`` to
every subcommand. ``backfill`` skips property rows whose actor no longer exists
and counts them, and its checkpoint file (``--checkpoint-file``, default
relative to the working directory) is kept only after a fault:

.. code-block:: bash

    actingweb-property-lookup report                  # read only
    actingweb-property-lookup backfill --apply        # rows, then markers
    actingweb-property-lookup mark-complete --apply   # ran the 3.13 backfill
    actingweb-property-lookup unmark --apply          # roll a name back

``backfill`` marks a name only when its pass finished with no fault and no
collision (two actors sharing an indexed value); the other names are still
marked. ``mark-complete`` refuses a name that has property rows and no
lookup rows unless ``--force``. The marker is an operator assertion that the
backfill ran: after copying data into a store with a tool that bypasses the
library, run ``backfill --apply`` again. ``scripts/backfill_property_lookup.py``
remains as a shim that delegates (its ``--dry-run`` is the command's default;
running without it means ``--apply``).

**Storage changes**

- *DynamoDB:* the markers are reserved rows in the existing
  ``<prefix>_property_lookup_v2`` table (``#meta#backfill#<name>`` and
  ``#meta#configured``); no new table. **The runtime role needs
  ``BatchGetItem`` on that table** whatever the auto-create setting: the
  startup check reads the markers with one ``BatchGetItem`` at every start,
  and a role without it refuses to start with
  ``PropertyLookupNotReady`` ("could not be checked"). It also needs
  ``PutItem`` there, for the markers an empty store writes when it marks
  itself ready. A policy that lists actions (``GetItem``, ``PutItem``,
  ``Query``, ...) rather than granting ``dynamodb:*`` is the usual way to
  miss ``BatchGetItem``: it was not needed before 3.16. You can drop the
  v1 ``<prefix>_property_lookup`` table and the ``property-index`` GSI on
  ``<prefix>_properties`` once the backfill is verified; nothing reads them.
- *PostgreSQL:* a new table ``property_lookup_backfill``. Run
  ``alembic upgrade head`` (revision ``f6a7b8c9d0e1``) **before** the deploy,
  or the startup check is refused as "could not be checked". The backfill
  inserts in primary-key batches that commit alone; run it off-peak on a large
  ``properties`` table.

**An indexed write and its lookup row now commit together**

Before 3.16 a DynamoDB indexed property write that could not write its
lookup row logged ``LOOKUP_TABLE_SYNC_FAILED`` and succeeded, leaving a value
that reverse lookup could never find (the legacy GSI had masked this for
older deployments). Now the property and its lookup row are one
``TransactWriteItems`` and a fault raises ``DbError`` (503), with nothing
written. PostgreSQL already rolled the pair back together. A value another
actor already holds is still a logged collision (``LOOKUP_COLLISION``), not a
failure: the property is written and the first owner keeps the lookup row.
An indexed write costs about twice the write units of a plain put on
DynamoDB; writes of non-indexed names are unchanged.

**Wrong prefix.** Markers written under a wrong ``AWS_DB_PREFIX`` land in
that prefix's (empty) tables, and the real tables stay unmarked and are
refused when the prefix is fixed. The maintenance command refuses to run
when the actors or properties table does not exist, so a wrong prefix is
never read as an empty store.

Custom database backends
------------------------

``DbSubscriptionSuspension.is_suspended`` must raise ``DbError`` on a read
fault (3.16), not answer ``False``.

A backend must live inside ``actingweb.db`` and follow the contract the
module docstring of ``actingweb.db.protocols`` states:

- accept ``*, strict: bool = True`` on every ``get`` (except
  ``DbProperty.get``, which takes none and always raises), ``fetch`` and
  ``get_bucket``, and ``consistent`` and ``ids_only`` on
  ``DbActor.get_by_creator``;
- raise ``DbError`` on a fault (``raise DbError(op) from e``), and answer it
  as absence only when ``strict=False``;
- answer ``True`` from a delete through a loaded handle when the row is gone,
  absent rows included;
- keep ``delete_attr_conditional`` and ``conditional_update_attr`` answering
  ``True`` only when that call changed the row (and ``False`` on a fault: the
  single-use consume step relies on it);
- implement ``DbAttribute.create_attr_if_absent(actor_id, bucket, name, data,
  timestamp=None, ttl_seconds=None) -> bool`` as one conditional write that
  creates the row, or replaces one whose stored ``ttl_timestamp`` is in the
  past, and answers ``True``; ``False`` when a live row (or another bucket's
  row) holds the name; ``True`` when a lost condition leaves a JSON-equal
  row (an SDK-retried create); ``ValueError`` for a missing
  ``actor_id``, ``bucket`` or ``name``; ``DbError`` on a fault. This is
  the one conditional write that raises on a fault;
- implement ``DbSubscription.increment_seq(actor_id=None, peerid=None,
  subid=None)`` as one atomic update that returns the new sequence number
  (None when the row is gone). The library no longer writes ``previous + 1``
  through ``modify(seqnr=...)``, which let two concurrent changes share a
  number;
- take ``callback`` on ``DbSubscription.create`` and ``modify`` as a bool
  only (``None`` on ``modify`` leaves it), raising ``TypeError`` before any
  I/O for anything else;
- raise ``DbError`` from ``DbAttribute.delete_expired`` on a fault rather
  than answer 0 (a backend with native TTL may still answer 0 without
  doing anything);
- implement ``DbActorList.iter_rows(*, consistent=False, rate_limit=None)``,
  yielding each actor as ``{"id", "creator"}`` as it is read, without
  holding the fleet in memory, and raising ``DbError`` on a fault.
  ``actingweb-mark-actors-vouched``, ``actingweb-migrate-property-lists``
  and ``actingweb-verify-property-lists`` call it.
  (``actingweb-verify-orphans`` reads the DynamoDB or PostgreSQL tables
  directly and supports only those two backends.)

A backend without ``strict`` fails with ``TypeError`` at its first call; one
without ``increment_seq`` fails with ``AttributeError`` at its first diff;
one without ``iter_rows`` stops those three commands before they scan.

For reverse lookup (see `One reverse-lookup mechanism`_) a backend must also:

- accept a keyword-only, required ``indexed_properties: list[str]`` in the
  constructors of ``DbProperty`` and ``DbPropertyList`` and no
  ``use_lookup_table`` (``actingweb.db.get_property`` and
  ``get_property_list`` pass only ``indexed_properties``);
- write an indexed property and its lookup row together or not at all, and
  raise ``DbError`` from the property write when it cannot;
- provide four module-level functions in its ``property_lookup`` module:
  ``read_readiness(names)`` returning ``(marked names, recorded name set or
  None)``, ``mark_backfilled(names)``, ``unmark(names)`` and
  ``record_configured(names)``; a missing table or any other fault raises
  ``DbError``.

For creator uniqueness, ``DbActor`` must also:

- accept a keyword-only ``unique_creator: bool = False`` in its constructor
  (``actingweb.db.get_actor`` passes ``config.unique_creator``; without it
  construction fails with ``TypeError``) and a keyword-only
  ``replace_holder`` on ``create``;
- with the flag set, raise ``CreatorTaken`` from ``create`` and ``modify``
  when another actor holds a non-exempt creator (the rules are in
  ``actingweb.db.creator_rules``);
- implement ``replace_creator_holder(old_id, *, actor_id, creator,
  passphrase)``, creating ``actor_id`` and moving the creator from
  ``old_id`` in one atomic step (``CreatorTaken`` when ``old_id`` no longer
  holds it), ``get_creator_holder(creator, *, strict=True)``, a
  consistent read of the one holder, and ``release_stale_creator(creator,
  actor_id)``, which removes a record naming an actor that is gone or holds
  another creator and returns whether it did (a backend whose uniqueness
  lives on the actor row, as PostgreSQL's does, returns False).

Direct ``check_and_verify_auth()`` callers
------------------------------------------

``check_and_verify_auth()``, ``check_and_verify_auth_async()`` and ``Auth()``
take ``config`` as a **required keyword-only** argument. Before, an omitted
``config`` silently built a default ``Config()``, whose library defaults
(``devtest=True``, the demo host) are not the application's. A call without it
raises ``TypeError: ... missing 1 required keyword-only argument: 'config'``;
one that passed it positionally (``Auth(actor_id, "basic", config)``) raises
``TypeError`` too. The documented examples already pass ``config=``. Separately,
``Config(fqdn=..., proto=...)`` without ``oauth=`` now derives
``oauth["redirect_uri"]`` from that host instead of the default one.

Advertised option tags
----------------------

``/meta/actingweb/supported`` (``Config.aw_supported``) advertises what the
application serves. ``sessions`` and ``onewaytrust`` are gone (no route; trust
is always reciprocal), ``listproperties`` is added, ``www`` is listed only when
the web UI is on and ``oauth`` only when a provider is configured. The value is
computed from the configuration on every read, so ``with_mcp()`` and the other
builder calls cannot leave it stale, and ``Config.aw_supported`` is **read-only**
(an assignment raises ``AttributeError``). A peer that keyed on ``sessions`` or
``onewaytrust`` finds neither; none that we know of does.

Permission pattern escapes
--------------------------

A permission pattern now treats a backslash as an escape: ``\*``, ``\?`` and
``\\`` are a literal ``*``, ``?`` and backslash, so a pattern that contains one
changes meaning. The peer-permission cache and the callbacks' property filters
used ``fnmatch`` and now use the evaluator's matcher: no ``[seq]`` character
classes (a ``[`` is literal), case-sensitive (``fnmatch`` folded case on some
platforms), and a pattern ending in ``://`` with no wildcard (``files://``) also
matches what follows it, as it already did in the evaluator (before, a stored peer
pattern ``files://`` matched only that exact name, and the callbacks' revoke
deleted only the list of that name). The matcher is linear-time, so a peer-supplied pattern with many
``*`` cannot hang a request. Check any rule you wrote that holds a backslash or
``[``; none shipped, in the demo or in the docs does. See
:doc:`../guides/access-control` ("Pattern syntax").

``POST /mcp`` parse errors
--------------------------

A ``POST /mcp`` whose body is empty or not JSON now answers **400 with JSON-RPC
``-32700 Parse error``** (``id: null``), before authentication. It used to be
treated as an empty request. A well-formed request without credentials still gets
the 401 challenge, so discovery works; only a client that probes with an empty
body now sees 400 where it saw 401.

SPA error codes
---------------

Every error the SPA token endpoints answer (``/oauth/spa/*``, ``/oauth/revoke``
and ``/oauth/logout``) now carries a stable code, in the response header
``X-ActingWeb-Error`` and in the JSON body's ``code`` key beside ``error: true``.
The codes are ``invalid_request``, ``unsupported_grant_type``, ``invalid_grant``,
``refresh_token_reused``, ``access_denied``, ``not_found``, ``server_error`` and
``temporarily_unavailable``; the table is in :doc:`../guides/spa-authentication`.
The database fault handler's answers on the SPA and ``/oauth/*`` paths carry the
header too (``temporarily_unavailable``, ``conflict``, ``internal_error``), and
``Access-Control-Expose-Headers`` on those answers now lists ``Retry-After`` and
``X-ActingWeb-Error``.

This is the predicate rule 7 of the SPA guide now uses: **a 401 on refresh that
carries the header is the library's and final** (sign the user out); one without
it is not the library's (a gateway's, say) and keeps the session. A client that
treated every 401 as final is unaffected. The gateway in front of the application
must pass the header through and, for a cross-origin browser, list it in its
exposed headers; the body ``code`` arrives either way. The email endpoints
(``/oauth/email``) keep their own ``code`` values.

Creator uniqueness
------------------

Before 3.16 ``with_unique_creator()`` made ``Actor.create`` list the
creator's actors and refuse when it found one. Two concurrent sign-ins or
factory posts could both pass that check, a creator change was never
checked, and a factory post with the existing actor's passphrase got that
actor back. In 3.16 the database holds one actor per creator:

- **DynamoDB:** a ``<prefix>_creators`` table, one item per held creator.
  An actor create puts the actor and its record in one
  ``TransactWriteItems``; a creator change updates the actor and puts the
  new record in one. The old record (after a delete or a creator change) is
  then removed by a separate conditional delete, only if it still names
  the actor; a fault there is logged and leaves a record that ``report``
  lists. The actor table and its scans are unchanged.
- **PostgreSQL:** the partial unique index ``ux_actors_creator`` on
  ``actors (creator)`` for every value other than ``trustee``, ``creator``
  and the empty string. It is built by the command below, not by an Alembic
  migration (a migration would fail on every deployment with duplicates),
  and ``alembic revision --autogenerate`` ignores it.

``trustee``, ``creator`` and the empty creator stay shared. Addresses (values
with ``@``) are lowercased before they are stored; provider ids such as
``apple:…`` compare exactly.

The flag is **on by default**. An application that cannot take the step
below yet opts out with ``with_unique_creator(False)``, which keeps the
duplicate-tolerant path (the adoption rules for several actors sharing a
creator). Code that builds ``Config()`` and creates actors without
``integrate_*`` must call ``ActingWebApp.check_ready()`` as an
application does. Without it, with uniqueness on and ``enable --apply`` not yet run, every actor create and creator change (a rename, a holder replacement) for a non-exempt creator, including the OAuth2 system actor bootstrap, raises ``DbError`` (``database error during actor create``, or ``actor modify`` and ``actor replace holder`` for the changes; 503 through the integrations, and retrying does not clear it) on both backends. Run ``actingweb-unique-creators enable --apply`` first, or call ``check_ready()``, which names the command. ``BaseHandler`` no longer defaults its ``config``, so a
handler built without one raises ``ValueError`` instead of enforcing a store
that was never checked.

.. _Step 0:

**Step 0, for every deployment that keeps the default.** Neither the index nor
the table can be switched on while actors share a creator, so in order,
with the application's environment (``DATABASE_BACKEND``, the database
settings, ``AWS_DB_PREFIX``, credentials).

**DynamoDB permissions.** If your IAM policy lists tables by name, add
``<prefix>_creators`` to the application's role (``GetItem``, ``PutItem``,
``UpdateItem``, ``DeleteItem``, and ``DescribeTable`` unless table
auto-creation is off) before step 4, plus ``ConditionCheckItem`` on the
actor table, and give the role that runs the command ``CreateTable`` and
``Scan`` on it as well. Without them the startup
check cannot read the table and the application refuses to start.

1. ``actingweb-unique-creators report`` lists actors sharing a creator
   (including addresses that differ only by case) and exits 1 if there are
   any.
2. ``actingweb-unique-creators resolve`` prints which actor of each group it
   keeps and how it renames the others; ``resolve --apply`` does it. With
   ``force_email_prop_as_creator`` on, add ``--default-creator-to-email``:
   it moves each actor left with the default creator (``creator``) to its
   stored email. A create no longer does that (3.15 swept them on every
   default-creator create). Run it again after step 3: only then does the
   move go through the uniqueness check, and before it a concurrent sign-in
   can still take an address.
3. ``actingweb-unique-creators enable --apply`` creates and fills the
   DynamoDB table or builds the PostgreSQL index ``CONCURRENTLY`` (it
   refuses while duplicates remain).
4. Deploy 3.16.
5. ``actingweb-unique-creators enable --apply`` again: it records actors the
   old processes created during the deploy. Re-running it is safe.
6. ``actingweb-unique-creators report``. If it lists anything (an actor
   created in the window with a creator another actor holds, or a record
   left by a delete in an old process), run ``resolve --apply``, then
   ``enable --apply``.

Close the factory for the window with ``with_open_factory(False)`` if you
can. The application refuses to start with the flag on until step 3 has run
(``UniqueCreatorNotReady``); call ``ActingWebApp.check_ready()`` yourself if
you use neither integration. If the check cannot reach the database, the
application refuses to start as well (``UniqueCreatorNotReady``, naming the
fault): starting unchecked on DynamoDB, against an empty auto-created
``creators`` table, would let every existing user's next sign-in create a
second actor.

``report``, ``resolve --apply`` and ``enable --apply`` are safe to run
against live traffic with the flag on (steps 5 and 6): what they list as
damage is confirmed by a consistent read of the actor or record, and a
record they write commits only while its actor is as read, so an actor
created or renamed while they run is left alone. ``resolve`` points the
record at the actor it keeps before it renames the others, so a sign-in
during the run lands on the kept actor. ``enable`` lists a
creator recorded for another actor and carries on, and writes the
backfill-complete item only when it listed nothing. ``--creator`` is
refused for ``enable`` and ``disable``.

**Which actor ``resolve`` keeps.** The best by marker (vouched, then
unvouched, then ``factory``), then the oldest (PostgreSQL's ``created_at``;
on DynamoDB the ``created_at`` the OAuth sign-in stores, unknown ages last),
then the lowest id. A group with an actor whose marker cannot be read is
skipped and reported. ``resolve --keep <id>`` overrides the rule for that
id's group. The others are renamed to ``<creator>#dup-<hash>`` and their
stored ``email`` is cleared, so ``force_email_prop_as_creator`` cannot undo
the rename; nothing is deleted. **A renamed actor no longer opens with its
old creator** (basic auth, OAuth sign-in): choose the kept actor with
``--keep`` before ``enable``, or change creators with
``ActorInterface.modify_creator`` afterwards.

**Rolling back.** Turn the flag off and wait until every process that ran
with it has stopped (one still serving would find no holder for anybody and
create duplicates), then run
``actingweb-unique-creators disable --apply``. Re-running it finishes a run
that stopped part way. It drops the PostgreSQL
index, or deletes the DynamoDB backfill-complete item and every record (the
empty table can then be dropped by hand), so turning the flag on again
starts with Step 0 from the actors, not from records that went stale while
it was off. On PostgreSQL the index keeps answering ``CreatorTaken`` while
it exists, even with the flag off.

**What the flag changes once enabled:**

- A create or creator change for a creator another actor holds raises
  ``CreatorTaken``: ``ActorInterface.create`` and
  ``ActorInterface.modify_creator`` raise it,
  ``PUT /<id>/trust/trustee`` answers 409 and applies nothing else from the
  request, and a route of your own answers 409 through the app-level handler.
- The factory answers 403 "Creator already exists" for a held creator,
  whatever the passphrase. A client that relied on getting the existing
  actor back for its passphrase should keep the id and URL from the first
  201 and use basic auth on ``/<id>``, or sign in through OAuth.
- A sign-in that replaces a ``factory`` actor creates the successor first
  and moves the creator to it in the same backend step, then removes the
  squatter, so ``actor_created`` for the successor fires before
  ``actor_deleted`` for the squatter. There is no ranking of duplicates and
  no sibling sweep. If the squatter was renamed in the meantime the sign-in
  fails closed; if its deletion status cannot be read, it answers 503.
- An actor the sign-in would clean in place (no marker, or an unvouched
  one) answers 503 when its deletion status cannot be read, with or without
  the flag, and is left as it is.
- Two concurrent first sign-ins for one identifier (two tabs, a retried
  callback) both end on the actor the first one created; one that finds
  that actor before its ``auth_method`` marker is readable (only rows an
  older process wrote) answers 409 instead.
- A record whose actor is gone, or holds another creator now (left by a
  release that faulted, or by an old process during the rollout), is
  removed by the next sign-in for that creator, which then creates the
  owner's actor; the stale record never signs anyone in to that actor.
- A sign-in that loses the swap to a concurrent sign-in for the same
  squatter ends on the winner's successor.
- A DynamoDB create whose answer was lost after the transaction committed
  answers 503 although the actor exists; a retry then gets
  ``CreatorTaken``. ``report`` does not flag it: sign in, or look the
  creator up, to reach the actor.
- Two applications sharing one actor table can no longer both bootstrap
  their system actors (``system``, ``oauth2-system``).
- On DynamoDB a creator change writes the new ``creators`` record and the
  actor in one transaction, then releases the old record in a second
  step. Between the two the old creator still answers ``CreatorTaken``,
  for about one write's latency. A create for the old address in that
  moment fails and can be retried.
- On DynamoDB a ``creators`` record edited by hand to point at the wrong
  actor is not repaired by anything: a sign-in for that creator resolves
  through the record. ``report`` lists it as an orphaned record
  (``mismatch``), and nothing else finds it. Run ``report`` after any
  manual edit of the table.

- On DynamoDB an actor create, delete or creator change costs about 4-6
  write units instead of 1 (a transaction, and the conditional release of
  the old record). Only opted-in tables pay this.

**Scripts that write actors directly.** ``actingweb_mcp``'s
``scripts/restore_actor.py`` writes through ``DbActor``: either create
through ``Actor.create`` with the flag on, or run ``resolve --apply`` and
``enable --apply`` after it. ``report`` finds what such a script leaves.

**Consumer code to check:**

- Catch ``CreatorTaken`` from ``ActorInterface.create`` and
  ``modify_creator`` where you create or rename on the user's behalf, or let
  the app-level handler answer 409. Test for it before ``DbError``: it is a
  subclass, but a conflict, not an outage.
- A caller that relied on the factory returning the existing actor for a
  matching passphrase.
- Monitoring: ``actingweb-unique-creators report`` exits 1 when it finds
  anything, and 2 when the store cannot be read.

SPA ``prompt``
--------------

``POST /oauth/spa/authorize`` accepts ``"prompt": "select_account"``. It is
additive: ``consent`` is always sent. Google receives ``select_account
consent``; GitHub and Apple ignore it. ``GET /oauth/spa/config`` lists
``prompt_values`` and a per-provider ``prompt_supported`` (as does
``/oauth/config``; ``GET /?format=json`` lists ``prompt_values`` only). Any other value
answers ``400``. See :doc:`../guides/spa-authentication`.

Spanned list items
------------------

A property-list item is one storage row, so on DynamoDB an item cannot
exceed about 400 KB. Before 3.16 an oversized write failed with the untyped
``DbError("property write")``, and a consumer had to refuse large items with
its own rule. 3.16 adds two limits, ``list_item_span_threshold`` and
``list_item_max_bytes`` (``ActingWebApp.with_list_item_limits()``), and
spans a v2 item over the threshold across several rows. See
:doc:`../guides/property-lists` ("Items larger than one row") for the full
picture; what an upgrade needs:

- **Nothing changes shape in the actor's partition.** Existing rows keep
  their form, and a spanned item's body rows live in a separate side
  partition (``{actor_id}$aux``) that no dump or range read of the actor
  returns. A 380,000-byte item stays one row.
- **PostgreSQL is unchanged at its defaults** (no spanning, no ceiling). A
  deployment that develops on PostgreSQL and runs DynamoDB in production
  sets both limits in the app, so spanning happens in development too:

  .. code-block:: python

     app.with_list_item_limits(span_threshold=390_000, max_bytes=4 * 2**20)

- **Drop your own size rule and catch the typed error.** An item over
  ``list_item_max_bytes`` raises ``ListItemTooLargeError`` (a
  ``ValueError``, before any write); catch it ahead of generic
  ``ValueError`` handling. The REST handlers answer 413.
- **Size the ingress limit at your edge** (Flask ``MAX_CONTENT_LENGTH``, an
  ASGI body-limit middleware, a proxy's or gateway's body-size setting) to
  ``list_item_max_bytes`` plus room for the JSON around it. The library's
  limit is a storage bound, not an ingress guard.
- **Read bodies on demand.** ``items_with_handles(resolve=False)`` and
  ``to_list_from_rows(rows, resolve=False)`` skip spanned items' bodies
  (their slot holds ``UNRESOLVED``; the handle carries ``spanned`` and
  ``bytes``) and ``item_at(handle)`` reads one. A listing benefits only if
  title and metadata live outside the large item.
- **Diffs over the threshold are references.** A list diff whose blob would
  exceed the threshold carries ``"spanned": true`` and ``"bytes"`` instead
  of its values; the subscriber re-reads the list. A pre-3.16 subscriber
  answers ``unknown operation`` and stores nothing.
- **Rolling deploys.** Until every process runs 3.16, a pre-3.16 reader sees
  a spanned item as an envelope dict, a pre-3.16 ``clear()``/``delete()``
  leaves its bodies for the aged sweep, and a pre-3.16 actor delete leaves
  the side partition for ``actingweb-verify-orphans`` to report. The sweep
  tooling ships in the same release as the writer, so deploy 3.16
  everywhere before raising any client's size limit.
- **Refusals.** ``downgrade_to_v1`` refuses a list holding spanned items,
  ``migrate_to_v2()`` refuses a v1 list holding a dict item whose first key
  is ``__aw_env`` (``reason="envelope-shaped item"``), ``append`` and the
  other writers refuse such an item, and new list names may not contain
  ``$``.
- **Actor ids.** ``Actor.create`` and ``ActorInterface.create`` refuse a
  caller-supplied ``actor_id`` containing ``$`` or longer than 251
  characters (``ValueError``, before any write). Generated ids are 32 hex
  characters and unaffected. An existing actor whose id already holds a
  ``$`` (possible only through a consumer's own ids) keeps working, except
  that a spanning write on it raises ``ValueError`` before anything is
  written. **Audit before deploying** if your application supplies its own
  actor ids: look for any id containing ``$``. An actor whose id is another
  actor's id plus ``$aux`` would share that actor's side partition; 3.16
  detects it, logs an ERROR and skips the sweep when the other actor is
  deleted, but rename it.
- **Pre-3.16 items shaped like an envelope.** Only a stored value whose
  first key is ``__aw_env`` with exactly the value ``1`` is read as a
  storage envelope; any other value, including a pre-3.16 dict item
  ``{"__aw_env": "x", ...}``, reads as the plain item it is and is never
  removed by the sweep. A pre-3.16 v2 item ``{"__aw_env": 1, "v": ...}`` is
  read as an envelope (its ``v``). New writes refuse dict items carrying the
  key, and ``migrate_to_v2`` refuses them in v1 lists. If your items could
  carry that key with the value ``1``, check before deploying.
- **REST permission errors deny.** The REST property handlers answer 403
  when the permission evaluator raises, instead of falling back to the
  legacy ``access`` table (which allowed ``friend``, ``partner`` and
  ``admin`` every property method). A database fault still answers 503.
- **Three lifecycles.** A list's ``delete()`` reaps its side-partition rows;
  an actor delete reaps its partition and its side partition; anything else
  (a crash between bodies and head, a failed best-effort cleanup) waits for
  ``actingweb-verify-property-lists --repair --sweep-spans``, which removes
  orphan generations older than an hour. The default ``verify()`` does not
  count leaked bodies; ``verify(spans=True)`` does.
- **A broken span answers 409.** A spanned item whose body rows are missing
  raises ``ListItemSpanError`` (a ``ListCorruptionError``); the 409's
  ``remedy`` names ``--sweep-spans`` or ``delete_by_handle()``, and its
  ``detail`` carries the item's rank.
- **Limits.** ``list_item_max_bytes`` may be at most 9,999 times
  ``list_item_span_threshold`` (the most body rows a span names); a pair
  outside that raises ``ValueError`` where it is set.


Idempotent appends
------------------

``ListProperty.append_once(item, *, key)`` lets a client repeat a create
whose answer it never saw (a gateway that timed out while the server
finished the write) without making a second copy. It replaces a
find-then-append duplicate guard, which races. See
:doc:`../guides/property-lists` ("Idempotent appends") for the protocol
and its two windows; what a consumer does:

- **Mint the key with the first attempt and keep it with the draft**: a
  UUID4, or 128 random bits, never something guessable such as a title.
  Every repeat, from any page or device, sends the same key.
- **An answer means what it says.** ``created=True``: stored now.
  ``created=False``: already stored; ``result.item`` is the item the first
  call stored, whatever the repeat sent. There is no "pending" status.
  ``RuntimeError`` means the key-row create kept losing under contention
  (the item may be stored; repeat with the key); a ``DbError`` can follow a
  stored item (any exception after the item write can), and repeating
  with the key converges. Only an operator
  rewrite (``compact()``, ``repair_keys()``) or a delete running at the
  same moment can overtake an answer, so run those with writes quiesced.

  .. code-block:: python

     result = actor.property_lists.drafts.append_once(draft, key=draft_key)
     if not result.created and result.item != draft:
         ...  # the key was used for different content

- **A key is bound to its item.** Deleting the item frees the key, so a
  repeat that arrives after a user deleted the item stores it again.
- **Two repeats that overlap** both write; the loser deletes its copy, so a
  reader can see both for the length of that delete. If that delete
  faults, ``verify()`` reports ``duplicate_keyed_items`` once the copy is
  an hour old, and ``actingweb-verify-property-lists --repair`` (which runs
  the new ``ListProperty.repair_keys()``, no rebalance) removes it.
- **A repeat that finishes a stopped call announces it.** When the first
  call stored the item and stopped before its key row, the repeat returns
  ``created=False`` with ``announced=True`` and sends the diff (an
  ``insert`` at ``announce_index``) and the ``count_hint`` update the first
  call never made. Subscribers hear of an item at most once: a call that
  stops between its key row and its diff leaves the item unannounced.
- **Clocks.** ``verify()`` and the repairs leave alone what was written in
  the last hour, by the writer's clock: keep the hosts' clocks in sync.
- **v2 lists only.** ``extend()``, ``insert()`` and the REST handlers take
  no keys.
- **Behavior change:** the first ``append_once`` on a list makes it
  unreadable to pre-3.16 readers (they see the storage envelope as the
  item) and ``downgrade_to_v1`` refuses it. Deploy 3.16 everywhere before
  the first call.
- **SDK retries.** A keyed append recognises its own write when a
  conditional create retried by the SDK answers ``False`` after landing.
  Unkeyed ``append()``, ``extend()``, ``insert()`` and ``pop()`` still
  cannot; use ``append_once`` where a duplicate matters.


Cross-site requests
===================

A ``GET`` that carries a ``_method`` override changes state, and a browser
sends the ``SameSite=Lax`` session cookie (and cached basic-auth
credentials) on a top-level navigation any site starts. Every handler that
honours the override (``/<id>``, ``/properties``, ``/trust``,
``/subscriptions``, ``/actions``, ``/methods``, ``/callbacks`` and the web
UI) now requires the request to show it came from the application's own
pages:

- ``Sec-Fetch-Site: same-origin`` when the browser sends that header
  (``none``, ``same-site`` and ``cross-site`` are refused);
- otherwise an ``Origin``, then a ``Referer``, whose scheme, host and port
  are those of ``config.root`` (a base path does not matter; ``Origin:
  null`` is refused);
- a request with none of the three passes (a script, a peer), unless it
  carries the ``oauth_token`` session cookie.

Only requests with an ambient credential are checked: the session cookie,
or basic auth (browsers cache it). A request with an explicit Bearer token
and no cookie, such as an SPA calling the API cross-origin, is not. A
refused request answers 403 "Cross-site request refused" and changes
nothing. Every ``POST`` under ``/<id>/www`` is refused when the browser
reports a cross-site request, and the Flask and FastAPI integrations do not
let the session cookie, or a ``Basic`` header on any route but
``/oauth/token``, authenticate a ``POST``, ``PUT``, ``PATCH`` or ``DELETE``
that the browser reports as started by another site, a sibling subdomain
included. The token endpoint keeps a ``Basic`` header (an OAuth2 client's
``client_secret_basic``). A browser page on another origin that calls
actor routes with creator basic auth through ``fetch`` loses it: use an
OAuth2 Bearer token there. A browser form ``POST`` to ``/oauth/email`` that
the browser reports as started by another site, a sibling subdomain
included, answers 403 before anything is claimed, created or mailed, and no
request another site started gets a session cookie from that endpoint; a
JSON client still gets its token in the body. This needs the browser's
``Sec-Fetch-Site``, ``Origin`` and ``Referer`` to reach the application.

**Peer-supplied trust fields.** A peer's ``id`` must be letters, digits and
``_ . : @ + = -`` (at most 255 characters, starting with a letter or digit)
and its ``baseuri`` a plain ``http`` or ``https`` URL with no user info,
query or fragment. An incoming trust request outside those shapes answers
400, and so does a peer's ``PUT`` that changes its ``baseuri`` to one;
``create_reciprocal_trust`` returns ``False`` for such a URL, or for a peer
whose ``/meta`` names such an id. Ids the library makes for OAuth2 and MCP
trusts are not affected. The shipped templates no longer interpolate values
inside inline event handlers; if yours do, move the value to a ``data-``
attribute (HTML escaping does not protect a JavaScript string inside an
attribute).

**What to check:** a template or page of your own that links to a
``?_method=`` URL must be served from the application's origin (the shipped
templates are); a proxy must not strip ``Sec-Fetch-Site``, ``Origin`` and
``Referer``, or set them to another origin; a script that relied on
``?_method=`` with the session cookie must send the real method; a page on
another origin that posts the email form must send it as JSON.

Peer paths are bound to their peer
----------------------------------

Before 3.16 a callback was accepted without authentication, a peer could
reach another peer's subscriptions, permissions and trust row through any
access row that admitted it, and a trust request for an existing peer
replaced its trust row (see the 3.16 ``SECURITY`` entries in the changelog).
3.16 closes each of these; what an application may need to do:

**A row admits the method a request performs; a peer's own paths are the
``owner`` rows'.** An access row now admits only the HTTP method a request
performs: a PUT or DELETE (or a ``GET ?_method=PUT|DELETE``) is no longer
admitted by a GET row. A peer's own subscription
(``subscriptions/<id>/<subid>``) and its own trust row are admitted by the
built-in ``owner`` rows, which now compare with the peer the path names, so
a trust type whose ``acl_rules`` grant only GET on its subscription (the
pattern ``actingweb_mcp``'s ``subscriber`` type used) needs nothing new: its
subscribers clear their queue and are unsubscribed as before, and another
peer's PUT or DELETE answers 403. PUT and DELETE rows an application added
are harmless. The ``owner`` row on subscriptions is now ``("owner",
"subscriptions/<id>/<subid>", "GET,PUT,DELETE", "a")``: it never admits
creating a subscription, which stays with the relationship's own rows. An
application that reads ``config.access`` for the old ``("owner",
"subscriptions", "", "a")`` row finds the new one. Through the ``owner``
rows a peer also reads its own trust's permissions and may ``PUT`` its own
trust row (description, and a base URI whose ``/meta`` names it, 400
otherwise; approval and permissions stay the owner's). What a peer polls of
a ``properties`` subscription is filtered by its property permissions, as
its callbacks are; a change it may not read polls as ``{}``.

**Creating a trust toward a peer whose request waits.** A verified pending
request is approved (the peer is told and ``trust_fully_approved_local``
runs, not ``trust_initiated``, from ``POST /trust``, the web form and
``TrustManager``); a pending request that never verified is
replaced by the owner's own request, with the owner's secret.

**Callbacks are authenticated.** Every ``/callbacks`` request without
credentials answers 401 with a challenge. The two library branches,
``/callbacks/subscriptions/<peer>/<subid>`` and
``/callbacks/permissions/<peer>``, admit only the peer they name (403 for
anyone else, the actor's creator and an ``admin`` peer included). Only
``diff`` and ``resync`` callbacks are accepted on the subscription branch
(400). A low-granularity diff is fetched from the trust's stored base URI,
never from the callback's ``url``; ``FanOutManager`` therefore no longer
downgrades a large payload to a resource URL, it sends it in full and logs
a WARNING above ``max_payload_for_high_granularity``. A permission callback's timestamp may be at most five minutes
ahead of the receiver's clock (400 beyond, and for one that does not
parse): check the sender's clock if you see ``Refused a permission
callback``. A stored permission copy is written conditionally on the row
read, by a callback and by a permission query alike; a callback that keeps
losing to concurrent writers, or meets a storage fault, answers 503 with
``Retry-After``, and the
library's sender resends a 503 up to twice with the same body (a sender of
your own should do the same). ``PeerPermissionStore.store_permissions``
compares ``fetched_at`` with the stored row, not the process's cache, and
raises ``DbError`` on a fault; a failed permission query no longer
replaces a stored copy. On the generic branch, ``/callbacks/<name>``, any authenticated
caller reaches the application's hook as before, except for the library's
own names (``permissions``, ``subscription``, ``subscriptions``, ``www``,
``resource_*``), which answer 403: only a direct request to such a name is
affected, not the library's own dispatch. A third party that called
``/callbacks/<name>`` anonymously (a webhook) now receives 401. A peer
trustee's Basic retry after a refused bearer cannot succeed on the two peer
branches.

**Peers reach only their own rows.** ``/subscriptions/<peer>/…``,
``/permissions/<peer>`` and ``/trust/<type>/<peer>`` admit a peer only when
the path names it, whichever row admitted it (application ``acl_rules``
included); an ``admin`` peer is exempt there. ``GET /permissions/<peer>``
answers the same 403 for an unknown id and another peer's. ``GET
/subscriptions?peerid=`` and the root listing show a peer its own rows; a
peer view's and a client view's subscription listings show the accessor's
own. A peer on its own trust row (where an application row admits it) can no
longer approve the row or write its own permissions. The per-peer trust
``GET`` no longer returns another peer's ``secret`` to an ``admin`` peer,
and no peer changes another peer's base URI. An ``admin`` peer may still
delete any peer's trust row and then request a new one under that peer's
id; grant ``admin`` only to a peer you trust as much as the owner.

**Re-pairing.** A trust request (``POST /<actor>/trust/<relationship>``)
for a peer that already has a trust row is a re-pair: it is accepted only
with the trust's current secret as its bearer, and then only the secret
changes (the relationship, approval, base URI and grants stay, and no
``trust_request_received`` hook runs). The library's initiator
(``create_relationship``, ``create_reciprocal_trust``) does this itself for
a peer it already trusts, and only toward the stored base URI. Everything
else answers 403 and changes nothing:

- **A peer that moved:** the owner updates the stored base URI
  (``PUT /<actor>/trust/<relationship>/<peer>`` with ``{"baseuri": ...}``,
  as creator or trustee); the peer then re-pairs, or simply carries on.
- **A different relationship:** delete the trust and pair again.
- **A dead peer:** the creator removes the row locally, without contacting
  the peer: ``DELETE /<actor>/trust/<relationship>/<peer>?notify=false``.
- **One side removed its row locally** (``?notify=false`` or ``?peer=true``)
  and the other kept its own: the side without a row cannot prove the old
  secret, so the other side's owner removes its row with ``?notify=false``
  first, then they pair again.
- **A development tunnel whose address changes on every start** is a moved
  peer each time: give it a fixed domain, or delete and pair again.

A creation request is verified only when the requester returns its token
and its base URI's ``/meta`` names the peer id it claims. That catches a
peer sending the wrong base URI; it does not prove the id, since the
requester answers both, and actor ids are self-asserted. **With
auto-accept** (``auto_accept_default_relationship``) only a request that
verified is approved; any other is stored pending and answered 202, where
3.15 answered 201. A pending trust row, one stored unverified (a request
whose verification failed) and not yet approved by the owner, is replaced
by a later request that verifies; its custom permissions are not kept. An
approved row is the owner's, and only a re-pair with its secret changes it:
a host that verified under another actor's id blocks the real peer until
the owner removes the row (``?notify=false``). Where that matters, leave
auto-accept off so the owner approves each request. The per-peer trust
``GET`` now answers the row's own peer while the row is pending (202 with
the row), where it answered 403; an initiator uses it to confirm a re-pair
whose answer was lost. Trust rows replaced before 3.16 cannot be told
apart from legitimate ones; a deployment that suspects one deletes the
trust and pairs again, which also rotates its secret.

**Remove what was written before.** After every instance runs 3.16, in a
quiet period:

.. code-block:: bash

    actingweb-peer-state report          # what is stale
    actingweb-peer-state prune --apply   # remove it
    # A deployment that may have received forged permission copies for
    # peers it trusts also drops every copy; each is rebuilt at once by a
    # permission query to its peer ("rebuilt" / "not rebuilt"):
    actingweb-peer-state prune --all-permissions --apply

then restart the application's processes (they keep permissions they cached
until restarted). See :doc:`../guides/database-maintenance` ("Peer State
Written Before 3.16").

What stays the same
===================

* A provider access token or ``oauth_token`` cookie matched by email in
  ``auth.py`` does not adopt.
* Sibling actors that share a creator (``unique_creator`` off) and are not
  marked ``factory`` are not touched until a sign-in resolves to one: the rule
  acts on that actor. ``factory`` siblings are deleted by any sign-in that
  proves the address (item 2).
* A vouched actor that carries a deletion tombstone (a ``DELETE /<id>`` that
  stalled before its wipe) is returned to the sign-in as it is, as before.
* With ``unique_creator`` off, two concurrent first sign-ins may both run the
  rule; ``actor_adopted`` may fire twice. A second replacement reuses the
  successor the first one already created when it can read it, which narrows
  the race to two adjacent statements; it does not close it. With the flag on
  the database refuses the second create.
* Properties a squatter prefilled on a cleaned-in-place actor are reported,
  not removed.
* ``devtest`` must be off in production: it lets a caller rewrite ``_internal``,
  including ``auth_method``.
