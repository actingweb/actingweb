## Issues Found

### N1. The new `/www` migration advice tells a hook to return a value that renders as `True`
**Severity:** Medium. Owner-facing: it affects the application developer
who reads the guide. No peer can reach it.

**Description:** The iteration's docs say that a hook which returned
`False` for a page it serves now "returns what the page shows instead":
- `docs/guides/web-ui.rst`, "*What to check:* a hook that returned `False`
  for a page it does serve (for example after writing a response itself)
  returns what the page shows instead";
- `CHANGELOG.rst`, "it returns what the page shows instead".

`execute_callback_hooks` passes back a dict and reduces every other truthy
result to `True` (`actingweb/interface/hooks.py:837`, `:861-863`). So the
`isinstance(hook_result, str)` branch (`www.py:878-879`) cannot run, and
`output = str(hook_result)` (`:883`) writes `True`. A hook that follows the
advice gets:
- a string return: 200 with the body `True`;
- a hook that wrote its own response and returns `True`: `True` appended to
  that response.

Only a dict renders, either a `{"template": ...}` dict or JSON. The string
reduction predates this plan. The advice is new in 4f8c462.

**Location:** `docs/guides/web-ui.rst` (the `/www` paragraph),
`CHANGELOG.rst` (the `/www` 404 entry), `actingweb/interface/hooks.py:861-863`.

**Recommendation:** either
- say what does render: a `{"template": ..., "data": ...}` dict; or
- have `execute_callback_hooks` pass a `str` result through, so the existing
  `str` branch serves it, and test it.

### Low

The `clear()` fix (entries 4 and 5):
- **L1. A same-value write during a clear is still lost.**
  - **Where:** `property_store.py:287`, `if now[key] != value:`.
  - **How:** a client writes the identical value after the clear's diff is
    numbered but before the re-read. Its diff (N+1) follows the clear's
    (N), and then the clear deletes the name. The publisher no longer
    holds it; the subscriber does. This is the outcome M3 was rated
    Medium for.
  - **Why Low:** it needs the identical value, written inside the
    `register_diffs` call (milliseconds). The writer gains nothing, since
    the subscriber keeps the writer's own value. It is the same race as
    the accepted re-check-to-delete window.
  - **Docstring:** it names only the later window. This window is wider
    (the whole `register_diffs` call).
- **L2. The kept name's diff carries the raw stored text.**
  - **Where:** `property_store.py:292`, `blob=now[key]`.
  - **How:** an SDK write of the string `"5"` sends `"5"` (via
    `_register_diff`, `json.dumps`, `:110`). The kept-name diff sends `5`,
    which `_prepare_callback` turns into the integer 5 (`actor.py:4083-4086`).
  - **Why Low:** the REST writer already sends the stored text raw
    (`properties.py:1735`), so the protocol has this ambiguity today.
  - **The test** pins the raw form (`test_callback_delivery_actor.py:159`).
  - **Also:** a non-`DbError` from this `register_diffs` escapes `clear()`
    halfway through the deletes.
- **L3. The clear's unit and the kept name's unit for one remote subscriber
  are sent concurrently.**
  - **Where:** `actor.py:5922`, `deferred.extend(units)`;
    `callback_sender.py:296-312` (the pool).
  - **How:** this breaks the sender's rule "a unit's sends in order". A
    library receiver parks N+1 as a gap and applies it after N
    (`callback_processor.py:1148`), so it converges. A receiver that
    applies diffs in arrival order may end with the name deleted.
  - **Fix:** merge the held units per subscriber before `deliver`.
- **L4. The deferral state lives on the `Actor` instance**
  (`actor.py:5613`). Only an application that shares one `Actor` across
  threads is affected: its concurrent writes join the clear's batch. A
  delivery error cannot mask the clear's own exception, because `deliver`
  folds every send's error (`callback_sender.py:236`, `:246`, `:262`).

Other fixes:
- **L5.** The `/www` 404 is a blank page. The browser shows nothing, and
  only the status says what happened.
- **L6. `raw_body` is now bytes on the authenticated callback path.**
  - A hook that returns its `data` unchanged makes `json.dumps(hook_result)`
    raise (`callbacks.py:932`), which answers 500.
  - Body fields named `headers` or `raw_body` are overwritten (documented in
    `hooks-reference.rst`).
  - No demo or docs example echoes `data`.
- **L7. A publisher list whose items can never be fetched keeps the rebuild
  owed** (`remote_storage.py:1024`). This is bounded: an attempt sets
  `rebuilt_at` whether it succeeds or not (`callback_processor.py:488-503`),
  so it costs one baseline per `REBUILD_INTERVAL_SECONDS`.
- **L8. With `auto_storage` off, a polled resync marker reaches the data
  hooks as an empty `diff`** (`subscription_manager.py:1418`, `:1431`;
  `:2401`). An application that keeps its own replica is not told to
  rebuild. Before the fix it was told nothing at all.
- **L9. An item index of 10^18 or more is not an item path**
  (`properties.py:344`). `GET /properties/<list>/<19 digits>` answers the
  whole list (`:969`), as any non-index segment does, where it would have
  answered the item 404.
- **L10. Clearing `PUT`:**
  - `{"sequence": 5.0}` is now 400; it cleared through 5 before
    (`handlers/subscription.py:535`).
  - `{"sequence": -1}` answers 204 and clears nothing (`:557`).
- **L11. Hygiene:**
  - The new block in `_resource_went` is unreachable, since its one caller
    has parsed the parent already (`actor.py:5981-5983`, caller `:5789`).
  - A second `to_dict()` runs on every clear (`property_store.py:283`).
  - `_request_headers()` is built twice on the anonymous path
    (`callbacks.py:331`).
  - `_Peer.__init__` has no `-> None`
    (`tests/integration/test_property_item_paths.py:446`; predates the
    iteration).
- **L12. Credential headers other than `Authorization` and `Cookie`** (such
  as `Proxy-Authorization` and `X-Api-Key`) reach an authenticated
  callback hook (`callbacks.py:34`). The caller sent them to the receiving
  application's own hook. The security review ruled out exposure.
